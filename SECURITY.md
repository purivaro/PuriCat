# Security

Describes the security posture of the code on 2026-11-16. PuriCat is in early development: the v0.1.0 download is signed with a Developer ID and notarized, but there has been no external review, and it should not be used with production data yet.

Labels: **Implemented & verified**, **Implemented, not yet verified**, **Planned (Phase N)**. Evidence is in [TESTING.md](TESTING.md).

## Threat model

### Assets

| Asset | Where it lives |
|---|---|
| Database passwords | OS credential store only; in backend memory while a session is open |
| Passwords of the accounts the users dialog creates or changes | Typed or generated in the web view and held in the form's memory until the dialog moves on; sent to the backend for each preview and for the run, and back only inside a preview the user asked to see; on the system clipboard once copied. Not stored by PuriCat; the server keeps its own hash or verifier — and a PostgreSQL server that logs statements keeps the statement (see "Users and privileges") |
| Database contents | The user's servers; pages of rows in app memory while a tab is open; the full rows of a query tab's last run in backend memory (up to 100,000 rows per result); files the user exports |
| Connection metadata (hosts, user names, CA paths) | `puricat.db` in the app-data directory |
| SQL the user wrote | `puricat.db`: the text of open query tabs — also the text of a SQL file opened into one with "Open SQL file…" — the scripts the user saved and the history of runs (see "SQL console") |
| SQL the AI ran to read rows, and SQL it proposed | `puricat.db`: the AI activity log, with password literals masked (see "AI database tools"). An approved proposal is also in the connection's SQL history |
| Integrity of the user's data | The servers. PuriCat writes to them only when the user saves staged grid edits, runs a previewed Smart Paste (see "Write path"), creates, changes or drops a database from a form or runs one of four `FLUSH` statements from a MySQL connection's menu (see "Schema changes through a form"), creates an account, gives one another password or drops one from the users dialog (see "Users and privileges"), runs SQL in a query tab — typed there, or placed there from an AI answer (see "SQL console", "AI chat") — or approves SQL the AI proposed (see "AI database tools"). The AI itself writes to nothing: it is given no tool that writes |
| AI CLI accounts | Owned by the CLIs. PuriCat reads only an install and sign-in flag, and starts the CLI under the user's account for each chat turn; it never sees a token |
| What is sent to an AI provider | The user's chat messages, earlier answers and, when sharing is on, the schema context and the SQL of the active query tab (see "AI chat"). With the database tools on, also what the tools return: catalogue details and — only at the "Structure and rows" level — **rows** (see "AI database tools"). The conversation itself, with every tool result, lives in web view memory only |

### Trust boundaries

| Boundary | Trusted side | Untrusted side |
|---|---|---|
| IPC | Rust backend | Web view content |
| Database protocol | PuriCat | Server responses, object names and cell values |
| Subprocess | PuriCat | Output of spawned tools, including every answer a model writes |
| The socket of a chat turn with tools | PuriCat, which serves the tools | Whatever connects to it: the CLI's relay, and in principle any process of the same OS user that finds it while the turn runs. Every request is treated as a model's: it can only call the turn's tools |
| AI provider | — | The CLI's provider service: what a chat turn sends leaves the machine under the user's own account and that provider's terms |
| Network | — | Everything between the app and a database server |
| Update server | PuriCat's release key (its public half is compiled into the app) | GitHub and the network on the way to it: the manifest and the package they return. Only the package's signature is believed |
| Local machine | The logged-in OS user | Other local users |

Out of scope: an attacker who already runs code as the logged-in user or as root, and a compromised operating system.

### Threats and mitigations

| Threat | Mitigation | Status |
|---|---|---|
| Password disclosed through files, logs or the UI | Stored only in the OS credential store; no IPC command returns one; connections use typed options, not URLs, so driver errors do not carry it | Implemented & verified (Keychain round trip; MySQL auth failure does not echo the password) |
| Script running in the web view escalates to the system | No shell, filesystem or HTTP capability; CSP `script-src 'self'`; all effects go through 97 typed commands plus plain-text clipboard read and write and the native Save dialog | Implemented; not penetration-tested. Script in the web view could read the clipboard, could call `apply_changes` or `apply_paste` on an open connection, could create, alter or drop a database on an open connection that is not read-only (`create_database`, `alter_database`, `drop_database` — the name it must send along to confirm a drop is no obstacle to a script), rename, empty or drop a table or a view there (`apply_table_change`, with the same typed name), create a view or replace a view's query there (`save_view`), create an account, give one another password or drop one there (`create_user`, `change_password`, `drop_user`, again with the typed name; the server's own accounts, the connection's own and a PostgreSQL superuser stay refused) and run a `FLUSH` there (`flush_server`), could show the Open dialog for a SQL file and read the text of the file the user then picks (`pick_sql_file`), could run any SQL on an open connection through `run_sql`, could make the backend write an export file to any path the OS user may write (`export_result`), and could send any text to an AI provider under the user's account through `agent_send` — with Codex, whose sandboxed shell tool can read local files, that is a way to read files the web view cannot reach itself (see "AI chat"). It could also start a turn with the database tools at any level on an open connection, whatever the user chose, and approve a stored proposal (`agent_proposal_run`); neither gives it more than `run_sql` already does, except that rows read by a model go to the provider |
| SQL injection through object names, sort columns, edited or pasted values | Values are bind parameters, including pasted keys in Smart Paste lookups; identifiers pass through per-engine quoting; sort, edited, mapped and key columns must exist in the table's metadata | Implemented & verified (unit and live tests) |
| SQL injection through what is typed or chosen in the "New database" form | A `CREATE DATABASE` statement takes no bind parameters, so the builder is strict: the name, the owner and the template are each quoted as one identifier; a character set, collation or encoding must be a plain word (ASCII letters, digits, `_`, `-`) or the request is refused; an option of the other engine is refused (see "Schema changes through a form") | Implemented & verified (unit tests: hostile names stay one quoted identifier, hostile keywords are refused; live tests on MySQL 9.3.0 and PostgreSQL 16.13: a name with spaces, Thai letters and the engine's quote character is created under exactly that name) |
| A database is dropped by a slip of the hand | "Drop database…" shows the statement and what the database holds, and its button works only once the database's name has been typed exactly; `drop_database` takes the typed text and compares it with the name again. The server's own databases and the database a PostgreSQL connection is opened on are refused by the backend (see "Schema changes through a form") | The refusals: implemented & verified (unit and live tests). The button: verified through the UI on PostgreSQL (E2E: disabled with nothing typed and with the name one letter short). The comparison in the command: implemented, not yet verified (no test calls the command with a wrong text) |
| A table is emptied or dropped by a slip of the hand | "Empty table…" and "Drop table…" / "Drop view…" show the statement, say what the engine's statement does and about how many rows the table holds, and work only once the object's name has been typed exactly; `apply_table_change` takes the typed text and compares it with the name again. A read-only connection is refused (see "The table menu") | The button: verified through the UI on a MySQL table (E2E: disabled with nothing typed, and for Empty also with the table's former name typed). The comparison and the read-only refusal in the command: implemented, not yet verified (no test calls the command). The servers' refusals in a read-only session, and SQLite's for a file opened read-only: verified (live tests, SQLite test) |
| A statement that writes, or a second statement, rides in on the query typed in the view form | The query is the one piece of a form that is the user's own SQL and can be neither quoted nor bound. It must read as exactly one statement, and one that reads (`db::script::single_read`, the text check of the AI's query tool), and begin with `SELECT`, `WITH`, `VALUES` or `TABLE`; otherwise no statement is built. "Preview rows" runs the query on that tool's read-only path: a read-only transaction that is rolled back, on SQLite a handle that cannot write (see "Views through a form") | Implemented & verified (unit tests on the three engines: two statements, statements that write, a data-modifying `WITH`, a MySQL version comment each refused; live tests: a `DELETE` and a `SELECT` followed by a `DELETE` refused by the preview with the rows counted afterwards, on PostgreSQL also a function that deletes, stopped by the server's read-only transaction). The text check is a first filter, not a parser: see the limits of that section |
| A schema change runs that is not the one the user read | The statement in the form comes from the backend, from the function that builds it again at run time; the web view sends choices, never SQL | Implemented & verified below the UI (live tests: the statement returned by the creation equals the planned one). In the form the preview follows the choices with a short delay, during which the previous statement is dimmed and the button is disabled (see the limits of that section) |
| The password of an account being created or changed is disclosed — on screen, in an error, in a log, in the history | The statements shown hold `'••••••••'` in its place unless the user turns "show" on; the run builds the same text with the literal; a server's error is scrubbed of the password before it is shown; nothing goes to the SQL history, the AI activity log or a log of PuriCat's; the password crosses IPC from the web view to the backend, and back only inside a preview the user asked to see (see "Users and privileges") | Implemented & verified (unit tests: no masked statement holds the password, and each differs from the one that runs only by the literal; a server's message scrubbed of the password as typed and as written; E2E on MySQL: the mask, a generated password in the statement, the mask again after "hide"). **Known gap:** a PostgreSQL server that logs statements writes `CREATE ROLE` / `ALTER ROLE` with the password into its log |
| SQL injection through an account's name, host or password, or the database of a grant | Account statements take no bind parameters. Names and hosts are string literals with `'` doubled and a backslash refused; a MySQL password is written for the `sql_mode` read on the connection that runs it; a PostgreSQL password is refused while `standard_conforming_strings` is off; roles, databases and schemas are quoted identifiers; `_` and `%` are escaped in a MySQL grant's database (see "Users and privileges") | Implemented & verified (unit test: eight hostile texts as passwords, read back exactly in both MySQL modes and on PostgreSQL, and as names, one quoted name or refused; live tests: the password a server stored is exactly the hostile one and not the one trimmed — on MySQL by logging in, on PostgreSQL by md5; a database whose name the unescaped grant would match stays out of reach). `partial_revokes` on and `standard_conforming_strings` off: unit tests only |
| An account that matters is changed or dropped by a slip | The backend refuses a password change and a drop for the server's own accounts, the account the connection is logged in as and a PostgreSQL superuser; a drop needs the account's name typed, compared again in the backend; a read-only connection is refused (see "Users and privileges") | The refusals of those accounts: implemented & verified (live tests on both servers, for the plans and the runs). The typed name: the button verified through the UI on MySQL (E2E); the comparison in the command and the read-only refusal: implemented, not yet verified |
| Unintended writes while browsing | The browse path issues only `SELECT`; edits are staged and written only on Save; the Smart Paste preview issues only `SELECT`; optional server-enforced read-only session | Implemented & verified |
| A typed statement changes far more rows than intended | Impact guard: a row-changing statement runs in a guard transaction and is rolled back when it affected more rows than the connection's threshold (see "SQL console") | Implemented & verified (live tests, both engines; E2E on MySQL). Covers statements classified as row-changing only; the threshold is supplied by the UI |
| A destructive statement runs unnoticed | Confirmation listing `UPDATE` / `DELETE` without `WHERE`, `DROP`, `TRUNCATE`, `ALTER ... DROP`; every non-read statement on a Production-labelled connection | Implemented & verified for `DELETE` without `WHERE` (E2E, MySQL); the Production path has no automated test. UI only; reads the statement text |
| A runaway query, or a result that exhausts memory | Stop interrupts the statement on the server; a row cap per result (at most 100,000) stops a plain read | Implemented & verified in the backend (live tests, both engines); Stop is not exercised through the UI. Memory use at the cap has not been measured |
| Passwords typed in SQL end up in the local history | Password literals, in single or double quotes, are masked before a script is stored; a connection's history is deleted with the connection | Implemented & verified for the masking function (unit test). A heuristic; everything else in a script is stored as typed. The deletion has no test |
| A pasted block updates or duplicates the wrong rows | Rows are matched only on a catalogue-verified unique key chosen by the user; equality is evaluated by the database; duplicates, missing keys and malformed key values are never written, and block the run unless the user leaves them out; the outcome is previewed per row and re-checked per row at run time; one transaction (see "Smart Paste") | Implemented & verified in the backend for single-column and composite keys (live tests, both engines). Through the UI: UPSERT on a single-column key on MySQL only |
| A save overwrites a change made elsewhere, or touches the wrong rows | Complete-primary-key addressing, optimistic check on edited columns, exactly-one-row rule, one transaction with rollback (see "Write path") | Implemented & verified (live tests, both engines). DELETE checks the key only |

Enforced in the UI only, not by the backend |
| Unsaved edits lost by accident | Dirty-tab confirmation, locked paging / sorting / refresh, refusal to disconnect or change a connection with dirty tabs | Implemented; only the close confirmation is covered by E2E |
| Eavesdropping or tampering on the network | TLS modes up to `verify-full` | Only the default `prefer` has been run, against local servers; the stricter modes are implemented, not yet verified. `prefer` can be downgraded |
| Other local users read connection metadata | `puricat.db` mode 0600 on Unix | Implemented; the mode is not asserted by a test. No equivalent on Windows yet |
| Malicious cell content rendered as markup | React escapes text; cells are rendered as text nodes | Implemented, not specifically tested |
| Command injection through subprocess arguments | Fixed argument vectors built in Rust, no shell; the chat's prompt travels on stdin; the one user-influenced argument, the model name, is validated so it cannot be read as an option; with the database tools on, the vector also carries the path of PuriCat's own executable and of the turn's socket, both produced by PuriCat and encoded as JSON; see "Subprocess policy" | Implemented & verified for detection and for the chat (unit tests: the vectors with and without tools, including an executable path with a space in it, the model-name rule, the prompt on stdin and absent from the arguments; E2E on stand-in CLIs) |
| Test hooks abused in a shipped build | Hooks compiled only with `debug_assertions` | Implemented; no release build has been inspected to confirm |
| The AI reads or changes data on its own | By default the model is given no tools and no database access: it only writes text. SQL from an answer reaches a database only when the user opens it in a query tab and runs it, under the console's safeguards (see "AI chat"). The guarantee is about writing through SQL: a function with effects outside the transaction is not held back by it |
| SQL proposed by a model runs without the user meaning it to | `propose_sql` runs nothing. No tool returns a host, a user name, a password or the connection's name | Implemented & verified (unit test of the exact context text; E2E: the inspector's text, and the stand-ins' arguments and stdin holding neither the host nor the connection name, with and without tools; E2E: a step opens to the rows given, and the log holds the read). Schema names, the active query's text, whatever the user types and whatever a tool returns are sent as they are, cut for length only. There is no per-column redaction |
| Text in the database steers the model (prompt injection) | The context is fenced and declared reference data; a closing tag inside it is neutralised; tool results are declared data too. With the tools off a manipulated answer is still only text. With them on, an injection can make the model call tools: read the catalogue and, if rows are allowed, rows the account can read — which go to the provider — and propose SQL, which the user must approve. It cannot make the model write | Implemented; the fence is unit-tested. No test measures how a model reacts. The user must read SQL before running or approving it |
| Another local process uses the tools of a running turn | The socket lives in a directory of its own with mode 0700, under a random name, created so that an existing name fails; it exists only for the turn; no TCP port is opened | Implemented & verified for the mode and for the removal (unit test; the E2E runner checks the directory is gone). Not a defence against a process of the same OS user, which is out of scope here as elsewhere |
| An answer is rendered as markup or script | Answers go through a Markdown reader into React elements; nothing is inserted as HTML | Implemented & verified (Vitest: markup-looking text stays text; E2E: a streamed answer with a code block, bold and inline code) |
| What an AI read or changed cannot be reconstructed afterwards | A local activity log: every row-reading query, refused or failed read, proposal, approval, rejection and outcome, with the connection's name, the provider and the model | Implemented & verified (store unit test; E2E: the log holds `read`, `read_failed`, `proposed`, `approved`, `executed`, `blocked` and `rejected` entries of the run). A convenience record, not tamper-proof: it can be cleared, keeps 5,000 entries, and a failure to write it is ignored |

| SSH man-in-the-middle | Host-key verification | Planned (Phase 2b) |

## Credential handling

- Service name `PuriCat`, key `connection/<id>/password`, through `keyring` (macOS Keychain, Windows Credential Manager).
- The password crosses IPC in one direction only, UI to backend, when the user types it. The UI later learns `hasPassword` and sends `keep`, `set` or `clear`.
- Duplicating a connection copies the password inside the backend. Deleting a connection deletes its password.
- `puricat.db` holds profiles (host, port, user name, database, TLS settings, tags; for SQLite, the path of the file) but no secrets.
- A SQLite connection has no password: nothing is stored for it and the keychain is not asked when it is opened. An encrypted SQLite file cannot be opened.
- Passwords are held as ordinary strings in memory and are not zeroised.
- The passwords of the accounts the users dialog creates or changes are not credentials PuriCat keeps. One crosses IPC from the web view to the backend for each preview and for the run, comes back only inside a preview the user asked to see, and is written into the statement as a literal; it is not stored, logged or put in the history (see "Users and privileges").
- PuriCat never asks for, reads or stores AI account passwords or tokens. A chat turn starts the CLI with PuriCat's own environment (plus the tool's directory on `PATH`); PuriCat puts no database credential in the CLI's arguments, input or environment. That also holds with the database tools on: the CLI is given the path of PuriCat's executable and of a socket, and the tools run inside the app on the session it already holds.

## TLS

| Mode | Behaviour | Verified |
|---|---|---|
| `disable` | No TLS | No |
| `prefer` (default) | TLS if the server offers it; **not protected against downgrade** | Local servers: MySQL session reported encrypted, PostgreSQL reported not encrypted |
| `require` | Encrypt, do not verify the certificate | No |
| `verify-ca` | Encrypt and verify the chain | No |
| `verify-full` | Verify chain and host name (`VerifyIdentity` in MySQL) | No |

TLS is rustls with the OS root store; an extra CA file can be set per connection. The connection test reports whether the session is encrypted, as answered by the server. An open session does not display its TLS state anywhere yet. Open item: make a stricter mode the default for Production-labelled connections.

## Read-only sessions

A per-connection option runs `SET SESSION TRANSACTION READ ONLY` (MySQL) or `SET default_transaction_read_only = on` (PostgreSQL) on every pooled connection. `ServerInfo.readOnly` is the server's own answer, not the profile setting.

With the option on, the grid opens every table read-only and does not offer Smart Paste, `apply_changes` and `apply_paste` refuse before contacting the server (they check the saved profile), and if a write were sent anyway the server rejects it. The server-side refusal is verified by a live test on both engines. The "New database" form follows the same pattern: its button is disabled, `create_database` refuses a profile saved as read-only before contacting the server (no test of the command or of the button), and a `CREATE DATABASE` sent in a read-only session is rejected by both servers (live-tested). So do the forms of the database menu: `alter_database`, `drop_database` and `flush_server` refuse a profile saved as read-only (no test of the commands or of the buttons), and both servers reject `ALTER DATABASE` and `DROP DATABASE` in a read-only session (live-tested). Whether MySQL rejects a `FLUSH` in a read-only session was not tried. The users dialog disables "New user…", "Change password…" and "Drop user…", and `create_user`, `change_password` and `drop_user` refuse a profile saved as read-only (no test of the commands or of the buttons); whether the servers reject the account statements in a read-only session was not tried.

This is a guard rail, not a privilege boundary: a session can switch itself back with another `SET`. On the browse, save and Smart Paste paths that cannot happen, because PuriCat sends no user-supplied SQL there — only generated statements with bound values.

**In a query tab it can happen.** The tab's connection is acquired through the same pool, so it starts read-only and the server refuses a write (live-tested on MySQL; the PostgreSQL console was not run read-only). But the person typing can run `SET SESSION TRANSACTION READ WRITE` (MySQL) or `SET default_transaction_read_only = off` (PostgreSQL), or open a `READ WRITE` transaction, and then write. PuriCat does not filter such statements, and `run_sql` does not check the profile's read-only flag as `apply_changes` and `apply_paste` do. So in the SQL console the read-only option protects against accidents, not against the person at the keyboard. The switching statements themselves have not been run by a test in a query tab; this follows from the engines' documented behaviour.

The AI's reading tool does not rely on this option. It has a guarantee of its own that a statement cannot switch off (see "AI database tools"): `SET SESSION TRANSACTION READ WRITE`, `SET default_transaction_read_only = off`, `SET TRANSACTION READ WRITE` and a `COMMIT` followed by a write are among the attempts the live tests send through the tool and see refused. An approved proposal is different: it is SQL the user chose to run, on a console like a query tab's, and `agent_proposal_run` refuses it up front when the saved profile is read-only (no automated test).

The strong control is a database account that lacks write privileges.

### SQLite

There is no server to ask, so the option means something else and something stronger: the file is opened with `SQLITE_OPEN_READONLY`. Every connection PuriCat opens to it — the pool behind the grid and each query tab's own — is such a handle, and nothing sent on it can write: no statement switches it back (verified: an edit from the grid, `DELETE`, `CREATE TABLE` and `PRAGMA user_version` through the console are refused, and the file's bytes are unchanged afterwards). `ServerInfo.readOnly` reports how the file was opened.

In the connection form a **new** SQLite connection has the option on. It is a default, not a lock: the user turns it off to edit.

What it does not cover: `ATTACH` in a query tab opens another file, also read-only, and its contents can then be read there. That is the user's own statement in their own tab, on files their account can read anyway.

## SQLite files

- **Which file.** The path is part of the connection profile and comes from the web view, like a host name does: typed, pasted, or chosen in the native Open dialog. It must be absolute. PuriCat opens only a file that already exists (no `SQLITE_OPEN_CREATE`), so a wrong path cannot leave an empty database behind (verified).
- **What opening does to the file.** Nothing is written until a save or a statement that writes. No setting stored in the file is changed (journal mode, page size, …). SQLite may create its own `-wal` / `-shm` or `-journal` side files next to a file it writes, as it does for any program.
- **A file in use by another program** is read and written under SQLite's own locking. PuriCat waits for a lock for the connection timeout, then reports it. It adds no protection of its own; a save from the grid is one `BEGIN IMMEDIATE` transaction with the same optimistic check as on a server.
- **Values SQLite would accept without a word.** Text that is not a number is refused for a column declared to hold numbers, on the grid's save path, in Smart Paste and in the filter. The SQL console is not checked.
- **Foreign keys** are enforced on PuriCat's connections (`PRAGMA foreign_keys = ON`, per connection, not stored in the file).
- **Extensions.** PuriCat loads none and does not turn extension loading on, so SQLite's `load_extension()` function stays refused, as it is by default (verified in a query tab).
- **Not verified:** files from other programs and SQLite versions, an encrypted file (only a plain non-database file was tried), a hostile database file. SQLite is built to treat a database file as untrusted input only with extra settings (`trusted_schema = OFF`, defensive mode) that PuriCat does not set: **open files from sources you trust.**

## SQL injection defences

- All values in catalogue and data queries are bind parameters.
- Identifiers cannot be bound, so every name goes through `db::ident` (backticks, double quotes or brackets doubled; empty names and NUL bytes rejected).
- Sort columns are checked against the table's metadata before they are quoted.
- Reading one cell whole (`fetch_cell`) addresses the row by its complete primary key through the write path's own key clause — typed bind parameters — and the column must match the table's metadata before it is quoted.
- Row filters (`db::filter`) are built from a fixed set of operators. The column of a condition must match the table's metadata and is then quoted; its value — and the pattern of a text search, with `%`, `_` and the escape character made literal — is a bind parameter. So is every value of a list ("is one of" / "is not one of") and each end of a range ("is between"): one placeholder per value, each checked as a single value is; the SQL text of a list grows only by placeholders. "All" or "any" of the conditions is a boolean of the request that chooses between `AND` and `OR` (with each condition in its own parentheses); it puts no text of the request into the statement, and there is no free `WHERE` text. A request is bounded: at most 20 conditions, 200 values in a list, 1,000 bound values in all; more is refused before anything is sent. Unit tests assert the exact `WHERE` text and that a hostile value appears only in the parameter list — for a single value and, since 2026-11-20, for a value inside a list.
- Page size is limited to 1–1000; `LIMIT` and `OFFSET` are bound.
- On the write path every value — new values, key values and the original values used for the concurrency check — is a bind parameter. Column names from the UI must match the table's metadata and are then quoted by `db::ident`. A unit test confirms that hostile key and cell values never appear in the SQL text.
- Smart Paste lookups bind every pasted key value; the mapped, key and update column names must match the table's metadata and are quoted by `db::ident`. A unit test asserts the lookup's shape: one typed placeholder per key value, the values in the parameter list.
- The "New database" form produces DDL, where nothing can be bound. `db::ddl` therefore puts every typed or chosen piece in one of two places only: a quoted identifier (`db::ident`: the name, the owner, the template) or a keyword that must match a strict pattern (character set, collation, encoding: ASCII letters, digits, `_` and `-`, at most 64 characters). A unit test asserts that a hostile name stays one quoted identifier in the exact statement text and that hostile keywords are refused. The `ALTER DATABASE` and `DROP DATABASE` statements of the database menu are built under the same two rules (unit tests of the exact text, with names that contain the quote character). `FLUSH` takes nothing typed at all: the request names one of four kinds, and anything else does not deserialize (unit test). The statements of the table menu (`db::ddl::table_change`) hold identifiers only — the database or schema, the table and, for a rename, the new name — each quoted by `db::ident`; the words `TABLE`, `VIEW` and `MATERIALIZED VIEW` come from a closed list of kinds (unit tests of the exact text, with a table that already has a hostile name, a hostile schema and a hostile new name). Reading a definition binds the schema and the name as parameters on PostgreSQL and the name on SQLite; MySQL's `SHOW CREATE` cannot bind, so the database and the table are quoted identifiers there. The view form is the exception to the two places: its statement (`db::ddl::view_statements`) holds the view's name as a quoted identifier and, after `AS`, **the query as the user wrote it**. A query cannot be quoted or bound, so it is constrained instead: exactly one statement, a reading one, beginning with `SELECT`, `WITH`, `VALUES` or `TABLE` (`db::ddl::view_query` on `db::script::single_read`; unit tests of the exact statements, of a hostile name and of the refused queries). Reading a view's query for the edit form binds the names as parameters: the database and the view on MySQL, the schema and the view on PostgreSQL, the view on SQLite.
- The users dialog (`db::users`) writes account statements, which take no bind parameters either, and hold two kinds of text that `db::ident` does not cover: a MySQL account, named by two string literals (`'user'@'host'`), and a password. A name or a host is a string literal with `'` doubled, and a backslash or a NUL in it is refused, so it reads the same in every `sql_mode`. A MySQL password has `'` doubled and `\` doubled unless the session's `sql_mode` has `NO_BACKSLASH_ESCAPES`, read on the connection that then runs the statement; a PostgreSQL password has `'` doubled and is refused while `standard_conforming_strings` is off. Roles, databases and schemas are quoted identifiers. Reading an account binds its name (and on MySQL its host) as parameters, except MySQL's `SHOW GRANTS FOR`, which cannot bind and gets the account from the same builder. Details and tests: "Users and privileges".
- The SQL console is different by nature: it sends the SQL a person typed, as typed. What PuriCat adds around it is fixed text or safely built: `USE` with the database name quoted by `db::ident`, the guard's `START TRANSACTION` / `BEGIN` / `COMMIT` / `ROLLBACK`, `KILL QUERY` with the numeric connection id the server reported, and `pg_cancel_backend` with the backend pid as a bind parameter.

## Write path

Staged edits are saved by `db::write` and the engine modules ([ADR 0013](docs/adr/0013-staged-edits-and-optimistic-saves.md)). These rules are enforced in the backend, independent of the UI, unless noted.

| Defence | Detail | Status |
|---|---|---|
| Parameters only | Values travel as text parameters; none is interpolated into SQL | Implemented & verified |
| Identifier quoting | Database, schema, table and column names go through `db::ident`; unknown, generated, binary and spatial columns are refused before any SQL is sent | Implemented & verified |
| Complete-key addressing | Every UPDATE and DELETE names the full primary key with non-NULL values; a partial key, a missing key column or a keyless table is refused | Implemented & verified |
| Optimistic concurrency | Each UPDATE also requires every edited column to still render to the text the user saw; otherwise the save fails with a `conflict` error | Implemented & verified |
| Exactly one row | A statement that affects zero rows or more than one row aborts the save | Implemented & verified |
| One transaction | Deletes, then updates, then inserts, in a single transaction; any error or conflict rolls everything back, including statements that had succeeded | Implemented & verified |
| Size limit | At most 10,000 row changes per save | Implemented, not yet verified (no test exercises the limit) |
| Strict input | MySQL sessions add `STRICT_ALL_TABLES`; PostgreSQL parameters are cast to the column's bare type so the assignment enforces length and precision | Implemented & verified |
| What is reviewed is what runs | The review dialog's plan and the executed plan come from the same function. The plan is rebuilt at save time from the same change set and fresh metadata, not cached | Implemented; the equality of the two plans is by construction, not asserted by a test |
| Review policy | UI-enforced: review is mandatory for Production-labelled connections, any delete, and more touched rows than `bulkReviewRows` (default 10, set per connection) | Implemented & verified for deletes only |
| Read-only profile | `apply_changes` refuses when the saved profile is read-only | Implemented, not yet verified (the server-side refusal is verified) |

### Smart Paste

Smart Paste ([ADR 0014](docs/adr/0014-smart-paste-match-then-write.md)) writes through the same planner and executor as grid saves, so the backend rules of the table above (parameters only, identifier quoting, complete-key addressing, optimistic concurrency, exactly one row, one transaction, strict input) apply to it, with the chosen key in place of the primary key. The grid's review dialog and row threshold do not; the preview takes their place. What it adds, enforced in the backend unless noted:

| Defence | Detail | Status |
|---|---|---|
| Verified matching key | UPDATE and UPSERT need a key; the key must be the primary key or a plain unique index read from the catalogue at analysis time, and every key column must be mapped. Unique indexes over a column prefix or an expression (MySQL) and partial or expression unique indexes (PostgreSQL) do not qualify. Anything else is refused, whatever the UI sent | Implemented & verified (unit and live tests; the MySQL exclusion of expression indexes has no test) |
| Database-evaluated equality | Pasted keys are compared with stored keys inside parameterised lookup queries, so type and collation rules are the server's. PuriCat never decides that two keys are equal by comparing text, except to flag exact-text repeats within the paste | Implemented & verified (case-insensitive key on MySQL, case-sensitive on PostgreSQL) |
| Well-formed key values | A key value for an integer column must be a whole number: `12abc`, `1.9`, `1e2` and ` 1` are invalid rows. Other key columns get the value pre-checks (number shape, declared length). Such rows are never sent to the database, so MySQL's lenient `CAST('12abc' AS SIGNED)` cannot match row 12 | Implemented & verified (unit and live tests, both engines). Key values of other types that the database coerces (dates, for example) are not pre-validated beyond those checks |
| No ambiguous rows | A pasted row without a key value, two pasted rows with the same key, a pasted key matching more than one existing row, and (INSERT with a key) a key that already exists are problems. A row with a problem never reaches the statements that run. One such row blocks the whole run unless the request carries `skipProblems`, which the UI sets only from the checkbox in the preview; then both rows of a duplicated key are left out, never one of them | Implemented & verified. Two spellings of one key are duplicates when both reach the same existing row, in one 40-row lookup (unit and live tests) or in different lookups (unit test with simulated answers) |
| Read-only preview | `analyze_paste` issues only catalogue queries and `SELECT`s | Implemented & verified (row count unchanged after a preview) |
| Re-analysis before the run | `apply_paste` analyses the table again and refuses with a `conflict` error unless it reproduces the fingerprint of the preview the user approved. The fingerprint covers every row's status and changed columns (not the stored values, which the optimistic check guards), so a change that leaves the counts equal is caught | Implemented & verified (live tests, both engines: re-running an approved paste is refused; so is an outcome with the same counts but different rows) |
| Optimistic concurrency | UPDATEs address the row by the key as the database rendered it and require every changed column to still hold the value seen by the re-analysis | Implemented & verified through the shared planner; no Smart Paste test changes a row between analysis and write |
| One transaction, exactly one row per statement | A driver error, a wrong row count or a cancel rolls back everything, including statements that had succeeded | Implemented & verified (an impossible date after a valid row; cancel after 50 of 130 statements) |
| Cancellation | "Stop and roll back" sets a flag that is read before each statement. While a run is in flight the dialog cannot be dismissed (Esc, outside click and the close button are blocked), so the outcome is always shown | Implemented & verified for the executor's stop callback (live test); the flag itself, `cancel_job`, the button and the blocked dismissal are not exercised by a test |
| Size limit | At most 10,000 pasted rows per run | Implemented, not yet verified |
| Generated keys are never written | An auto-increment or identity key column may be used to match; its pasted value is never inserted or updated. In INSERT mode a pasted generated key that is not found is an invalid row, not a row inserted under another id; a blank key inserts | Implemented & verified |
| Read-only profile | `apply_paste` refuses when the saved profile is read-only; the UI does not show the button on a read-only tab | Implemented, not yet verified |
| Production connections | UI only: a red warning and a danger-styled Run button. No typed confirmation, and the grid's row threshold does not apply; the preview is always required | Implemented, not yet verified |

Smart Paste limitations:

- **The preview requirement is a UI rule plus a fingerprint check.** The backend cannot tell whether a human saw the preview; it only requires the caller to state the fingerprint a fresh analysis produces, which `analyze_paste` returns.
- **The re-analysis is not in the write transaction.** Its lookups run on pooled connections just before the transaction starts. A change made in between is caught by the optimistic check (updates) or by the unique index (inserts), and the run rolls back; a row classified as unchanged or unmatched is simply not touched.
- **"Unchanged" is decided by PuriCat, not by the server.** A pasted value that is plainly the stored one in another spelling (a decimal number, a date or time without a time zone, a PostgreSQL boolean) is not a change; everything else that differs as text is counted and run as an update, even when it stores the same value. The rule errs towards "changed": a wrong "unchanged" would leave a row alone that the user meant to change, so only spellings the servers were seen to store identically are accepted (live tests on both engines).
- **Key values of non-integer types are pre-checked only generically.** Integer keys must be whole numbers (see the table). A key value of another type that the database coerces, such as a date, gets only the number-shape and length checks and is then cast and compared by the server; a malformed one has not been tested on either engine.
- **The SQL statements are not shown.** The preview lists the operation per row and the changed columns, not the statement text that the grid's review dialog shows.
- **A stop request that arrives after the last statement has started does not prevent the commit.**

Data-integrity limitations to know about:

- **DELETE checks the key only.** A row that was changed elsewhere after it was loaded, but still exists, is deleted without a conflict. Only a row that is already gone is reported.
- **The concurrency check covers edited columns only.** A concurrent change to another column of the same row is not detected, and is not overwritten either, because only edited columns are written.
- **The comparison is on the server's text rendering.** Types whose text form depends on session settings compare correctly only while those settings match the session that loaded the page; PuriCat's sessions are configured identically, so this holds within one connection profile.
- **PostgreSQL sessions run in UTC.** The driver (sqlx 0.8) always sends `TimeZone=UTC` at start-up. `timestamptz` values are therefore shown in UTC with an explicit `+00` offset (unambiguous), a `timestamptz` typed without an offset is read as UTC, and `now()`-based defaults of `timestamp without time zone` columns — including those filled in for a row inserted through the grid — are computed in UTC rather than in the server's configured zone. Not fixed; a per-connection session time zone is Planned (Phase 2b). MySQL sessions keep the server's time zone (verified by a live test).
- **No client-side validation in the grid.** Invalid input is rejected by the server at Save, not while typing. Smart Paste adds a few cheap pre-checks; the server remains the authority there too.
- **No audit log of saves.** Saves and Smart Paste runs are not recorded anywhere by PuriCat. (What the AI read and proposed is logged; see "AI database tools".) The SQL history is a convenience, not an audit log: it covers query tabs and approved AI proposals only, keeps 1,000 entries, can be cleared, and a failure to write it is ignored.
- **Policy lives in the UI.** The review step and the keyless-table rule (the backend would accept INSERT on a keyless table) are not enforced by the IPC layer.

## Schema changes through a form

Since 2026-11-19 PuriCat issues statements that change a server's schema and that the user did not type ([ADR 0019](docs/adr/0019-schema-changes-through-forms.md)): `CREATE DATABASE` from the "New database" form, and `ALTER DATABASE` and `DROP DATABASE` from a database's menu, on a MySQL or PostgreSQL connection. Until then DDL reached a server only as SQL typed in a query tab, or proposed by the AI and approved. Since 2026-11-20 the menu of a table or a view adds a rename, `TRUNCATE TABLE` (on SQLite `DELETE FROM`) and `DROP TABLE` / `VIEW` / `MATERIALIZED VIEW`, on SQLite as well. The same day a form for views added `CREATE VIEW` and `CREATE OR REPLACE VIEW` (on SQLite `DROP VIEW` and `CREATE VIEW`), the first of these statements that holds SQL the user wrote. No form creates a table or an index, or changes a table's columns. This part is about creating a database; what editing and dropping one add is under "Editing and dropping a database, FLUSH, SQL files" below, the table menu under "The table menu: definition, rename, empty, drop", and the view form under "Views through a form: the one statement that holds the user's SQL".

| Defence | Detail | Status |
|---|---|---|
| One builder | `db::ddl::create_database` builds the statement. `plan_create_database` returns its text for the form and runs nothing; `create_database` calls the same function again and runs what it returns. The web view sends the choices (a name and options), never SQL | Implemented & verified (live tests on both engines: planning creates nothing; the statement returned by the creation is the planned one). In the end-to-end test the form's preview must show the expected statement before the button is pressed |
| Names are one identifier | The name, and on PostgreSQL the owner and the template, are quoted by `db::ident` with the quote character doubled; a NUL character is refused. The name is trimmed; an empty one and one that is too long (more than 64 characters on MySQL, more than 63 bytes on PostgreSQL, which would otherwise shorten it silently) are refused | Implemented & verified (unit tests of the exact text for hostile names; live tests: a name with spaces, Thai letters and the quote character) |
| Keywords must be plain words | A character set, collation or encoding is a keyword to the server, not an identifier, so it cannot be made safe by identifier quoting. It is let through only if it consists of ASCII letters, digits, `_` and `-` (at most 64); otherwise the request is refused before anything is sent | Implemented & verified (unit test: a semicolon, a space, a quote, a backtick and Thai letters are each refused, for MySQL's character set and for PostgreSQL's encoding) |
| Nothing is dropped silently | An option that belongs to the other engine is refused, not ignored; a SQLite connection is refused | Implemented & verified (unit test; live test for SQLite) |
| Read-only connection | The form says so and disables its button; `create_database` refuses a profile saved as read-only; the server refuses `CREATE DATABASE` in a read-only session | The server's refusal: implemented & verified (live tests, MySQL and PostgreSQL, nothing created). The command's refusal and the disabled button: implemented, not yet verified |
| Production-labelled connection | A red warning in the form and a danger-styled button, "Create on production" | Implemented, not yet verified (no test opens the form on such a connection) |
| The server's refusal is shown, not hidden | A name that exists, an unknown character set, a role that does not exist, an encoding the template does not allow, a missing privilege: the server's own message is shown in the form, which stays open | Implemented & verified below the UI for the first three (live tests, with nothing left behind) and through the UI for a name that exists on MySQL (E2E: the message appears in the open form; its text is recorded, not asserted). A missing privilege has not been tried |
| Where it runs | On a pooled connection of the open session, as that session's account; on PostgreSQL on the database the session was opened on, outside a transaction | Implemented & verified on both engines (live tests) |

Limits:

- **No bind parameters.** The statement is text; the two rules above (quoted identifier, or strict keyword) are what stands between a typed value and the server. They are small and unit-tested, and they are the whole defence.
- **No typed confirmation for a creation, and no review step.** On a Production-labelled connection the form warns and colours the button; one click still creates the database. The "review larger saves" threshold does not apply: it counts rows, and this is one statement that touches none. The statement is always in view before the click.
- **The policy is in the UI.** The backend enforces the builder's rules and the read-only flag of the saved profile. The Production warning and the disabled button are the form's. A script running in the web view could call `create_database` on any open connection that is not read-only; it can already run any SQL there through `run_sql`.
- **Not recorded.** A database created through the form is in neither the SQL history (which holds what ran in query tabs and approved AI proposals) nor any audit log. PuriCat keeps no trace of it; the server's own logs are the only record.
- **The preview follows the form after a short delay.** The statement is asked for 120 ms after the last change and shown when the answer arrives. Until then the form still shows the statement of the previous choices, dimmed, and the button is disabled: the form keeps the choices each answer belongs to and lets a statement run only while it is the one for the choices on screen. Read from the code; no test presses the button inside that window.
- **The real control is the account.** PuriCat creates the database as the connected account, with whatever that account may do. An account without the privilege is refused by the server; that refusal has not been observed in a test.
- **A PostgreSQL name beyond 63 bytes** would be shortened by the server with only a notice; PuriCat refuses it first ([DATABASE_COMPATIBILITY.md](DATABASE_COMPATIBILITY.md), "New database"). The refusal has a unit test; the limit assumes the usual server build.
- **Not verified:** a read-only or Production-labelled connection through the UI, the bundled app under the production CSP, Thai and the dark theme, MySQL other than 9.3.0, MariaDB, PostgreSQL other than 16.13, and real mouse and keyboard input (the end-to-end test sends synthetic events).

### Editing and dropping a database, FLUSH, SQL files

Added the same day ([ADR 0019](docs/adr/0019-schema-changes-through-forms.md), section 7; what each engine allows is in [DATABASE_COMPATIBILITY.md](DATABASE_COMPATIBILITY.md), "Database menu"). A drop is the first thing a PuriCat form does that destroys data, so it gets more than the creation did.

| Defence | Detail | Status |
|---|---|---|
| The statements shown are the statements run | `db::ddl::alter_database` returns the `ALTER DATABASE` statements as a list, in the order they run; `db::ddl::drop_database` returns the one `DROP DATABASE`. `plan_alter_database` and `plan_drop_database` return the text and run nothing; `alter_database` and `drop_database` call the same builders again and run what they return. The web view sends a database name and what should differ, never SQL | Implemented & verified (live tests on both engines: planning changes and drops nothing; the statements returned by the run equal the planned ones). In the end-to-end test the preview must show the exact `ALTER DATABASE` text before "Save changes" is pressed, on both engines |
| Only the change is sent | The edit form sends what differs from the database as the server describes it now; nothing changed means no statement and a disabled button, and the builder refuses an empty change as well | Implemented & verified for the builder (unit and live tests). The form's comparison: through the UI for one change per engine (E2E) |
| A drop needs the name typed | The button is disabled until the text typed equals the database's name exactly. `drop_database` receives that text and refuses unless it equals the name: the confirmation is part of the request, not a state of the form | The button: implemented & verified through the UI on PostgreSQL (E2E). The comparison in the command: implemented, not yet verified |
| The user sees what a drop takes with it | The form counts the tables and views of the database and says how many open table tabs of it will close. The count is best effort: if it cannot be made, no number is shown and the drop is still possible | Implemented & verified below the UI for the count (live tests: a table and a view give 2, an empty database 0, a database that cannot be looked into none). Through the UI the sentence is recorded, not asserted |
| The server's own databases | MySQL's `information_schema`, `mysql`, `performance_schema` and `sys` (any letter case) and PostgreSQL's `postgres`, `template0` and `template1` are refused by the builder, for a change and for a drop, whatever the form sent | Implemented & verified (unit and live tests). In the explorer the two menu items are hidden for MySQL's four; for PostgreSQL's `postgres` they are shown and the refusal appears in the form (read from the code; not tried) |
| The database the session is opened on (PostgreSQL) | A drop and a rename are refused before anything is sent, with the reason | Implemented & verified (live test) |
| Several statements, one outcome (PostgreSQL) | An owner change and a rename are sent as one simple query, which the server runs as one transaction | Implemented & verified (live test: with a rename the server refuses, the owner is unchanged) |
| Read-only connection | The forms say so and disable their button; `alter_database`, `drop_database` and `flush_server` refuse a profile saved as read-only; the servers refuse `ALTER DATABASE` and `DROP DATABASE` in a read-only session | The servers' refusals: implemented & verified (live tests, both engines, the database still there). The commands' refusals and the disabled buttons: implemented, not yet verified |
| Production-labelled connection | A red warning in each form; a danger-styled button, "Drop on production" for a drop. A change and a `FLUSH` need one click, as a creation does; a drop needs the typed name on every connection, labelled or not | Implemented, not yet verified (no test opens these forms on such a connection) |
| Unsaved work in the database | The forms do not drop or rename while a table tab of the database has unsaved edits or a query tab opened on it has an open transaction | Implemented, not yet verified. The check is the form's; see the limits |
| PuriCat's own connections | Before a drop or a rename the backend closes the session's pooled connections to the database and the consoles of query tabs opened on it, so PuriCat is not what keeps a PostgreSQL database in use. Nothing is done to other clients: there is no `WITH (FORCE)` | The pooled connections: implemented & verified (live test on PostgreSQL: a database the session had just read is renamed and dropped). The consoles of query tabs: implemented, not yet verified — no test has a query tab open on the database |
| `FLUSH` is four fixed statements | `FLUSH PRIVILEGES`, `FLUSH TABLES`, `FLUSH LOGS`, `FLUSH STATUS`. The request names the kind; the text is a constant of the backend. The form shows the statement and a sentence on what it does before "Run". Refused on any engine but MySQL. `FLUSH HOSTS` is not offered | Implemented & verified (unit test: the four kinds, an unknown kind does not deserialize; live test on MySQL 9.3.0: Privileges, Tables and Status run, PostgreSQL and SQLite refused; E2E: Status through the UI). `FLUSH LOGS` was run once by hand, not by a test |
| A SQL file is only text | "Open SQL file…" reads one file the user picked in the native Open dialog and puts its text into a new query tab. Nothing is run; from there the rules of "SQL console" apply, with its confirmation and impact guard. The file must be UTF-8 and at most 1 MB | The tab holding exactly the file's text: implemented & verified through the UI (E2E; the dialog is answered by the test hook). The size limit, the UTF-8 refusal and the removal of a byte-order mark: implemented, not yet verified (no test) |

Limits:

- **Dropping is as final as the server makes it.** PuriCat takes no backup first and has no undo. The typed name guards against a slip, not against a wrong decision.
- **A change or a rename has no typed confirmation**, also on a Production-labelled connection. A rename breaks every client that connects by the old name; the form shows the statement and, on Production, a warning, and one click runs it.
- **The typed name is not a defence against script in the web view.** It is checked in the backend so that no path through the form can skip it; a script that calls `drop_database` simply sends the name twice. Such a script can already run `DROP DATABASE` through `run_sql`.
- **The unsaved-work check is the form's, and it goes by the tab.** The backend does not know about staged edits. It releases the consoles of query tabs opened on the database without asking: a transaction open there is rolled back when the connection closes, and a statement still running there is interrupted (read from the code). The form holds back for an open transaction but not for a statement that is merely running. On MySQL a query tab opened on the connection's default database, or one that moved with `USE`, is not seen as a tab of the database at all.
- **The table count is information, not a guard.** It is read when the form opens, not again at the click, and an empty database is dropped with the same single confirmation as a full one.
- **`postgres` on PostgreSQL keeps its menu items.** The backend refuses; the explorer does not hide them, because it does not mark any PostgreSQL database as the server's own.
- **`FLUSH` can disturb a busy server.** `FLUSH TABLES` waits for running statements and makes others wait; `FLUSH LOGS` starts a new binary log file where binary logging is on. The form says this in a sentence and does not measure anything. `FLUSH PRIVILEGES` is deprecated in recent MySQL (9.3.0 answers with warning 1681); server warnings are not shown.
- **No Stop.** These statements run on a pooled connection, not on a console. While one waits, the form stays open and cannot be dismissed.
- **Not recorded.** As for a creation: neither the SQL history nor any log has what was changed, dropped or flushed.
- **`pick_sql_file` hands the file's text to the web view.** Unlike the table file of Smart Paste, which stays behind a token, the text of the chosen file is the command's answer — it has to be, to become the tab's text. The dialog is shown by the backend and the user chooses the file; the `.sql` extension is a filter of that dialog and is not checked afterwards, so whatever file the user picks is read if it is UTF-8 and within 1 MB. A script in the web view could open the dialog but cannot name a path. The text is then stored in `puricat.db` like any query tab's text, and with "Share context" on it is part of what an AI turn can be given (see "AI chat").
- **Not verified:** everything marked so in the table; a drop or a rename while another client is connected to a PostgreSQL database; an owner change through the UI; the Flush kinds other than Status through the UI; the forms in Thai and in the dark theme; the bundled app under the production CSP; MySQL other than 9.3.0, MariaDB, PostgreSQL other than 16.13.

Limits:

- **Emptying and dropping are as final as the server makes them.** No backup first, no undo. On MySQL `TRUNCATE` and `DROP` commit at once; on PostgreSQL and SQLite PuriCat runs the statement outside a transaction of its own, so it is final there too.
- **The typed name is not a defence against script in the web view**, as for a database: a script that calls `apply_table_change` sends the name twice, and can already run the same statement through `run_sql`.
- **A rename has no typed confirmation**, also on a Production-labelled connection. It breaks every query, view and client that uses the old name; the form shows the statement and, on Production, a warning.
- **Nothing is protected by name.** The database menu refuses the server's own databases; the table menu has no such list. A table of `mysql` or of a PostgreSQL catalogue schema has the same menu, and only the account's privileges and the server stand in the way (read from the code; not tried).
- **The row count is information, not a guard.** It is the engine's estimate, read when the form opens: absent on SQLite and for a PostgreSQL table that was never analysed, and on MySQL it can lag (seen once: "about 2 rows" for a table emptied a moment before).
- **The PostgreSQL definition of a table is PuriCat's reconstruction, not the server's statement.** The dialog says so and names what is left out. Someone who runs that text elsewhere and takes the result for a faithful copy would be wrong where the limits apply: grants and row-level-security policies are not in it ([DATABASE_COMPATIBILITY.md](DATABASE_COMPATIBILITY.md), "Table menu").

It is shown in the web view, and once opened in a query tab it is stored with the tab's text in `puricat.db` and, with "Share context" on, is part of what an AI turn can be given as the SQL of the tab in front (see "AI chat").
- **The unsaved-edit check is the form's, and it sees one tab.** A query tab with an open transaction that touches the table does not hold the form back, and the backend does not know about staged edits (read from the code; not tried).
- **No Stop, not recorded.** As for the database menu: the statement runs on a pooled connection, the form cannot be dismissed while it waits, and neither the SQL history nor any log has what was renamed, emptied or dropped.
- **Not verified:** everything marked so in the table; SQLite, views and materialized views through the UI (since the view form's end-to-end stage, one view has been dropped there: "Drop view…" on MySQL); a rename, an empty or a drop on PostgreSQL through the UI; the forms in Thai and in the dark theme; the bundled app under the production CSP; MySQL other than 9.3.0, MariaDB, PostgreSQL other than 16.13.

### Views through a form: the one statement that holds the user's SQL

Added on 2026-11-20 ([ADR 0019](docs/adr/0019-schema-changes-through-forms.md), section 9; the statements per engine are in [DATABASE_COMPATIBILITY.md](DATABASE_COMPATIBILITY.md), "Views through a form"). "New view…" and "Edit view…", on MySQL, PostgreSQL and SQLite. Every other form puts what was typed into a quoted identifier or a strictly matched keyword. A view's query fits neither: it is SQL, written by the user, and it goes into the statement as it is. What holds it is described here.

| Defence | Detail | Status |
|---|---|---|
| The statement shown is the statement run | `db::ddl::view_statements` writes `CREATE VIEW <name> AS` (or `CREATE OR REPLACE VIEW`; on SQLite `DROP VIEW` and `CREATE VIEW`) around the query. `plan_view` returns the statements and runs nothing; `save_view` calls the same function again and runs what it returns. The web view sends the view's place and name, the query and whether the view exists — the words around the query are never its own | Implemented & verified (live tests on both servers and the SQLite test: the statements returned by the save equal the planned ones; planning creates nothing, checked on MySQL). In the end-to-end test the form must show the exact `CREATE VIEW` and `CREATE OR REPLACE VIEW` text before each button is pressed (MySQL) |
| The name is one identifier | Quoted by `db::ident`, with the database (MySQL) or the schema (PostgreSQL); a new name is trimmed, and an empty one or one that is too long is refused | Implemented & verified (unit test: a name that tries to close the identifier and add `DROP TABLE` stays one quoted name; live tests with a name that holds a space) |
| The query is exactly one statement | `db::script::single_read` splits the text as the SQL console does — outside strings, quoted names and comments — and refuses anything but one statement. A final `;` is removed. On SQLite, where a whole script could be prepared, no other semicolon may be in the text at all | Implemented & verified (unit test on the three engines: `SELECT 1; SELECT 2`, a `DROP TABLE` after the query, the same behind a comment; E2E on MySQL: with `; DROP TABLE orders` added the statement disappears, a refusal is shown and "Create view" is disabled) |

| A preview cannot write | "Preview rows" does not run the view's statement. | Read-only connection | The form says so and disables its button; `save_view` refuses a profile saved as read-only; the server refuses the statement in a read-only session; a SQLite file opened read-only is refused by the session before anything runs. The command's refusal and the disabled button: implemented, not yet verified |
| Production-labelled connection | A red warning in the form and a danger-styled button. One click creates or replaces the view | Implemented, not yet verified (no test opens the form on such a connection) |

| Where it runs | MySQL: a connection taken out of the pool for this one statement, with the view's database selected, then closed — so the selected database does not stay behind on a pooled connection. Limits:

- **At the save, the server confirms "one statement" too** (since 2026-11-20). `single_read` is a scanner with a list of rules, written as a first filter for a tool whose guarantee is what comes after it: the server's prepare and a read-only transaction. A preview has both. A save cannot have the transaction, so it goes through `Session::execute_one`: MySQL receives the statement as a prepared statement and PostgreSQL through the extended protocol, and both take exactly one statement — a text that holds a second one is refused by the server, whatever the scanner made of it, and neither runs. SQLite runs every statement of a text it is given, so there the query may hold no semicolon at all (a final one is removed), and without a semicolon no second statement can follow. Verified in live tests: on both servers a text of two statements given to `execute_one` is refused and leaves nothing behind; on a PostgreSQL database with `standard_conforming_strings = off` — where the scanner and the server disagree about where a string ends — a view's query that is one `SELECT` to the scanner and a `SELECT` and a `CREATE TABLE` to the server is refused at the save, with nothing created. Before this change the save went over the text protocol; with `psql` (the same protocol) that text created both the view and the table on such a database. On MySQL the save's connection takes the server's `sql_mode`, and a session with `NO_BACKSLASH_ESCAPES` was not tried for the save (it would mean changing the server-wide mode); the prepared statement holds there for the same reason as on PostgreSQL. The text is the user's own and on screen before it runs.
- **A view can call anything the account may call.** A query that reads may still name a function that writes or that acts outside the database. The preview's transaction stops a function that writes rows (verified on PostgreSQL); nothing stops one with effects outside the transaction, and the list of refused function names is a courtesy that an escaped identifier gets past. Once the view exists, whoever selects from it runs that query. The account's privileges are the real control, as everywhere.
- **The check also refuses harmless queries.** A string that contains a semicolon (SQLite), a column whose name contains `dblink` or `load_file`, a `FOR UPDATE` in a view: refused, with the reason. That is the price of using one rule for the tool and the form; such a view is typed as SQL in a query tab.
- **No typed confirmation, also on a Production-labelled connection.** Giving a view another query destroys no rows, and the statement is on screen. It can still break whatever reads the view: the form says so under the statement, and PostgreSQL refuses a change that removes a column.
- **An edit is a new statement, not a change of one.** On MySQL it carries no definer, algorithm or security clause; on SQLite the view is dropped first, and with it any `INSTEAD OF` trigger on it, which the form does not say (see [DATABASE_COMPATIBILITY.md](DATABASE_COMPATIBILITY.md), "Views through a form").
- **The query of an existing view comes into the web view.** "Edit view…" reads it (`view_select`), as "Definition…" does. Previewed rows are shown in the form and kept nowhere; neither the query nor the rows are given to an AI turn, since the form is not a tab.
- **The policy is in the UI, as for the other forms.** A script in the web view could call `save_view` on an open connection that is not read-only, and `preview_view_select` on any open one; both give it less than `run_sql` already does.
- **Nothing is protected by name**, as in the table menu: the "Views" group and the views of the server's own databases and schemas have the same items (read from the code; not tried).
- **No Stop for the save, not recorded.** The statement runs outside a console; neither the SQL history nor any log has what was created or replaced, or what was previewed.
- **Not verified:** everything marked so in the table; PostgreSQL and SQLite through the UI; "New view…" from a schema and from the "Views" group; a preview that fails and the 100-row limit through the UI; real typing in the form's editor (the end-to-end test sets its text); MySQL's answer for an account without `SHOW VIEW`; the form in Thai and in the dark theme; the bundled app under the production CSP; MySQL other than 9.3.0, MariaDB, PostgreSQL other than 16.13.

By PostgreSQL's default `log_min_error_statement`, a statement that fails is logged with its text as well (PostgreSQL's documentation; not tried). MySQL rewrites passwords out of the statements it logs. The remedy is to send a SCRAM verifier computed by PuriCat instead of the password, as `psql`'s `\password` does; it is not built. Other places where a server keeps the text of statements (activity and statistics views) were not looked at.
- **On screen and on the clipboard.** With "show" on, and once more after a creation or a change, the password is on screen. - **On PostgreSQL the setting is read on a pooled connection**, not on the very connection that runs the statement as on MySQL: `standard_conforming_strings` is read on a connection of the pool of `home`, and the role is created on a connection of the same pool. PuriCat sets it on none of them.

- **Not recorded, no Stop.** Neither the SQL history nor any log has what was created, changed or dropped; the statements run outside a console.

## SQL console

Query tabs run SQL the user typed ([ADR 0015](docs/adr/0015-sql-console.md)). The rules of "Write path" do not apply here: there are no generated statements, no key addressing and no optimistic check. What stands in their place:

| Defence | Detail | Status |
|---|---|---|
| A connection of its own per tab, set up like the pool's | Acquired through the session's pool, so MySQL strict mode and the read-only statement have run on it, then detached. Session state and transactions stay within the tab | Implemented & verified (live tests: session state on both engines; a read-only session refusing a write and six open consoles next to a working session on MySQL) |
| Splitting and classification in the backend | A dialect-aware scanner (`db::script`) finds statement boundaries and classifies each statement as `read`, `dml`, `ddl`, `transaction` or `other`; keywords inside strings, comments, quoted identifiers and dollar-quoted bodies do not count. A MySQL `--` comment starts, as in MySQL's own lexer, when a space or any control character follows the dashes: an invisible control character there once let a quote hide a second statement from the scanner, so that a query tab would have sent it inside the first one, unflagged (fixed 2026-11-20; unit test and a live check that MySQL reads `--` and a control character as a comment) | Implemented & verified (unit tests). **Not modelled:** MySQL's `NO_BACKSLASH_ESCAPES` and `ANSI_QUOTES` modes and PostgreSQL's `standard_conforming_strings = off`, under which the scanner and the server can disagree about where a string or a quoted name ends. A query tab sends each piece the scanner finds as text, so on a session in one of these modes a second statement could travel inside a piece and miss the confirmation meant for it. Known from live tests for `NO_BACKSLASH_ESCAPES` (the AI's tool) and `standard_conforming_strings = off` (the view form); for the query tab read from the code, not tried |
| Confirmation before running | UI: statements with a danger reason (`UPDATE` / `DELETE` without a top-level `WHERE`, `DROP`, `TRUNCATE`, `ALTER ... | Impact guard | Backend: a `dml` statement outside the user's own transaction runs in a guard transaction and is rolled back, status `blocked`, when the server reports more affected rows than the limit. SQL console limitations:

- **The statement classification is a convenience, not a boundary.** It reads keywords. A function called from a `SELECT` can write and is classified `read`: not confirmed, not guarded, and cancelled at the row cap (which rolls it back). `CALL`, `DO`, DDL and every `other` statement run unguarded.
- **DDL is not guarded, and MySQL DDL cannot be rolled back.** A confirmed `DROP` is final.
- **The guard measures the server's affected-row count.** Rows changed by triggers and foreign-key cascades are not counted. A statement whose reported count is not the number of rows it changed (`EXPLAIN ANALYZE UPDATE`, a data-modifying `WITH` ending in a `SELECT`) is judged by that count. Not tested.
- **The confirmation and the threshold are supplied by the UI.** `analyze_sql` only reports; `run_sql` runs the text it receives with the `changeLimit` it receives, and no limit is a valid value. The backend enforces the mechanism, not the policy.
- **"Run it without the limit" lifts the limit for the blocked statement and for every statement after it in that script**, not only for the one that was shown as blocked.
- **Transaction tracking reads the statement text.** A transaction opened inside a stored procedure or with `XA` is not seen, so the guard may send its own `START TRANSACTION` / `BEGIN` for a later statement; on MySQL that implicitly commits a transaction a procedure left open. A MySQL error that rolls back the whole transaction (a deadlock) is not noticed, so the badge stays and later statements run unguarded in autocommit. A successful MySQL DDL statement is taken as an implicit commit unless it contains the word `TEMPORARY` outside strings, comments and quoted identifiers (`CREATE TEMPORARY TABLE`, `DROP TEMPORARY TABLE`). That is a keyword test: DDL on an unquoted table or column that is itself named `temporary` is read the same way, and the badge then stays although the server committed. The rule has a unit test for the keyword test only; MySQL DDL inside a transaction is not run by any test.
- **Read-only is inherited, not enforced against SQL** (see "Read-only sessions").
- **History, query text and saved scripts are stored in clear.** `puricat.db` holds the text of every open query tab and every saved script exactly as typed (not masked; a saved script is the user's own text and masking would change it) and up to 1,000 history entries with only password literals masked. A script that contains a secret keeps it until the script is deleted; deleting a connection deletes its scripts. The mask is a heuristic: the first quoted literal (single or double quotes) within 48 characters of the keyword, and it can hide an unrelated literal (`WHERE password_hint = '...'`) or, on PostgreSQL, a double-quoted identifier. It pairs the first quote character it meets after the keyword with the next one of the same kind, so where the word `password` is itself a double-quoted identifier (`SET "password" = '...'`) the identifier's closing quote is taken as the opening one: the literal is then masked only together with everything up to the next double quote, and not at all when no double quote follows. That case follows from reading the code and has no test. Keys, tokens or personal data written into a script are stored as typed. The file is mode 0600 on Unix. Deleting a connection deletes its history entries; there is no setting to turn history off.
- **`export_result` takes its path from the web view.** The backend creates or overwrites that file with the result's contents, with the OS user's rights and default permissions. The Save dialog is the only caller in the UI; asking before an existing file is replaced is left to the operating system's dialog. Exported files contain database contents and are the user's to protect.
- **Results are held in memory**: the full rows of each tab's last run, up to 100,000 rows per result, until the next run or until the tab closes.
- **Stop depends on a free pooled connection** to carry the interrupt.

## Tauri capabilities and CSP

- Capabilities for the main window: `core:default`, `core:window:allow-start-dragging`, `clipboard-manager:allow-read-text`, `clipboard-manager:allow-write-text` and `dialog:allow-save`. The clipboard permissions belong to the official `tauri-plugin-clipboard-manager` and cover plain text only (no images, HTML or clearing); they exist for copy and paste in the grid, for Smart Paste, which reads the clipboard when its dialog opens and on "Read clipboard", for "Copy" on a code block of an AI answer (write only) and for copying a password in the users dialog (write only; PuriCat does not clear it afterwards). The users dialog added no permission and no CSP change.
- `dialog:allow-save` belongs to the official `tauri-plugin-dialog` and allows one thing: showing the native Save dialog and receiving the chosen path. The Open, message and confirm dialogs are not granted. The export file is written by the backend (`export_result`), not by the web view.
- **"Open SQL file…" needed no new permission either.** Its Open dialog is shown by the backend (`pick_sql_file`); `dialog:allow-open` is still not granted. What differs from the table file below is in "Editing and dropping a database, FLUSH, SQL files".
- **Opening a file for Smart Paste needed no new permission.** The Open dialog is shown by the backend (`pick_table_file`), not by the web view: the `dialog:allow-open` permission is still not granted. The web view receives the file's name and a random token, never its path, and `read_table_file` reads only the file last chosen in that dialog, by that token. So a script in the web view cannot ask the backend for a file the user did not pick. The file must have one of nine table extensions (`csv`, `tsv`, `tab`, `txt`, `xlsx`, `xlsm`, `xlsb`, `xls`, `ods`), checked before it is touched, and be at most 64 MB. Its content is treated as data only: it becomes rows of text for the wizard, and reaches the database as bind parameters like any pasted value. Workbooks are parsed by `calamine` and CSV by `csv`; formulas are not evaluated (the stored result is read) and macros are ignored.
- No shell, filesystem or HTTP plugin is registered and no such permission is granted. The dialog plugin pulls the `tauri-plugin-fs` crate in as a dependency, so its code is compiled into the binary, but the plugin is not registered in `src-tauri/src/lib.rs` and the web view cannot call it.
- Reading the clipboard needs no user gesture or prompt, so any script running in the web view could read it. The CSP and the absence of remote content are what guard this.
- Production CSP: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; connect-src ipc: http://ipc.localhost`. `'unsafe-inline'` is allowed for styles only. The SQL editor did not change it: Monaco's script, worker, stylesheet and icon font are bundled and served from the app itself. The end-to-end test records any CSP violation and fails on it; it passes against the bundled app, including the agent chat and database-tool stages ([TESTING.md](TESTING.md)).
- The development CSP (`devCsp`) is deliberately loose for the Vite dev server and applies to `pnpm tauri dev` only.
- The updater plugin (`tauri-plugin-updater`) is registered so that the backend can use it; **none of its permissions is granted**, so the web view cannot call it. See "App updates".
- Fonts are bundled; the web view loads nothing from the network. The agent chat added no capability and no CSP change, and neither did the database tools: the web view reaches the CLIs only through the `agent_*` commands, and it is the CLI process, not the app, that contacts the AI provider. The tools' socket is opened by the backend; the web view has no access to it.

## Subprocess policy

Subprocesses are started from Rust, never from the web view, with a fixed argument vector. The probes and the chat turns have a timeout and kill-on-drop; the `kill` helper, a backup and a restore (which can take as long as the database is large, and have a Stop button) and the short system tools of the last rows have none.

Points to be aware of:

- The fallback does use a shell. The command string is a constant plus a hard-coded binary name, so nothing untrusted is interpolated, but an interactive login shell runs the user's own start-up files.
- The binary that is executed is whichever `claude` or `codex` is found first, as in any terminal. PuriCat does not verify its origin. Since the chat, that binary also receives the prompt.
- A chat turn runs in `agent-scratch` inside the app-data directory, which PuriCat keeps empty, and inherits PuriCat's environment with the tool's directory prepended to `PATH`.
- The only argument a user can influence is the chat's model name: 1–100 characters out of ASCII letters, digits and `. _ : / @ - [ ]`, not starting with `-`, checked in the backend before the process is started.
- The bridge mode is decided by the first argument alone. Started with `--mcp-bridge`, the executable never initialises the app: no window, no settings store, no credential store. It connects to whatever socket path it is given and relays; it holds nothing worth taking. That the bridge exits with the turn was not checked separately (the end-to-end runner checks that the socket's directory is gone).
- stderr of a chat turn is read; its last non-empty line (at most 500 characters) is shown to the user when the CLI fails without a verdict in its stream.

AI chat limitations:

- **What is sent goes to the provider**, under the user's own account and that provider's terms. PuriCat cannot recall it.
- **Schema names and the active query can themselves be sensitive.** Table and column names are sent as they are. The SQL of the active query tab is sent with the history's password masking applied (`script::redact`, a heuristic) and otherwise as typed, so any other literal written in that tab goes along. There is no per-column redaction and no way to exclude a table.
- **The user's messages are not filtered.** Whatever is typed or pasted into the composer, including rows or credentials, is sent.
- **Switching the provider keeps the conversation.** The next turn resends the earlier questions and answers, with the context of the new message, to the other provider.
- **Database identifiers are untrusted text inside the prompt.** A table name, a column name or the active query can be written to steer the model. The fence and the instructions are a request to the model, not a control. With the tools off, an injection can at most change the text of an answer — which is why SQL from an answer must still be read before it is run. With the tools on it can do more (next section). On a connection whose schema other people can write to, treat answers accordingly.
- **Codex still has a shell tool.** PuriCat knows no documented option that removes it. It runs inside Codex's read-only sandbox, started in the empty scratch directory: its commands cannot write, and the sandbox blocks the network for them, but a manipulated Codex could read local files the user can read and put them in its answer. Claude Code runs with no built-in tools, with or without the database tools. PuriCat has not tested the sandbox; it relies on Codex's own description of it. The same reach is open to script running in the web view, which could ask Codex through `agent_send` to read a file.
- **Codex's successful path is unverified against the real CLI**; only its refusal was observed ([TESTING.md](TESTING.md)).
- **Sharing is a UI rule.** `agent_send` forwards the context text it receives and does not check where it came from or whether the switch is on; `agent_context` needs only an open connection. Script in the web view could send anything it can read.
- **The CLIs' own telemetry, update checks, logs and caches are outside PuriCat's control.** PuriCat itself sends nothing anywhere.
- **No version check.** A CLI release that drops an option or changes its stream fails the turn with its own message; one that changed what an option means would not be noticed.
- **Chat turns without tools are not logged.** The activity log records what the tools did (next section), not the conversation. SQL opened from an answer and run in a query tab appears in that tab's history like any other.
- **Backend messages are English only.**

AI database tools limitations:

- **Codex is unverified.** A Codex tool call has never been observed, nor whether `codex exec` lets an MCP tool run without asking. The access popover says so when Codex is selected; nothing stops the user from trying.
- **With the tools on, Claude Code runs without `--safe-mode`**, because that option also switches MCP servers off. What keeps the user's settings, instruction files, hooks and other MCP servers out is `--setting-sources ""`, `--strict-mcp-config` and `--disable-slash-commands`. Their combined effect on a real CLI was checked by hand once, not by a test.
- **Rows that are read leave the machine**, under the user's account with the provider and that provider's terms, as the database returned them and cut for length only. There is no per-column redaction and no way to exclude a table. The cap is 200 rows per query, not per turn.
- **The read-only guarantee is about writing through SQL.** A function with effects outside the transaction — ending another session, sleeping, reading a file on the server — can be called by a `SELECT` if the account may call it. The list of refused function names is matched as plain text, so an escaped spelling gets past it; it is a courtesy, not a boundary. An account without write privileges, and without such functions, remains the strong control.
- **The query tool is not confined to the database in front.** On MySQL a query can name another database the account can read; on either engine it reads whatever the account can read. Only the catalogue tools are confined. On SQLite a query reads the one file: `ATTACH` is refused by the tool, and a `SELECT` cannot open another file.
- **Prompt injection now reaches tools.** Text in a table name, a column name or a row can steer the model into calling them: reading more than the user asked about, which then goes to the provider, or proposing SQL written by whoever planted the text. The proposal still needs the user's approval, which is why the dialog shows the whole SQL — and why it has to be read.
- **Approval, and the level, are UI rules.** `agent_send` takes the tool scope from the web view and does not read the stored level; `agent_proposal_run` needs only the id of a stored proposal. Script in the web view could use both.
- **Same-user processes are trusted.** Another process of the same OS user that finds the socket during a turn can call the same tools, with the same limits.
- **Proposals run statement by statement, each committed on its own**, like a script in a query tab. An error leaves the earlier statements applied. A transaction the script leaves open is rolled back when its console closes.
- **Running what was held back lifts the limit for more than one statement.** "Run anyway" runs the statement the guard rolled back and every statement after it in the proposal, all without the limit. The third confirmation shows that whole text and says how many statements follow the held one; the limit is not applied again to them.
- **Names are resolved by the connection.** The reading tool and an approved proposal run on a connection opened on the tab's database, not its schema: on PostgreSQL unqualified names go through the session's `search_path`. The instructions for a turn with tools (`agent::tools_prompt`) now tell the model to write every table name with its schema on PostgreSQL. That is a request to the model, not a control: nothing checks a query or a proposal for it, no unit test asserts the sentence, and it was in the build of one real-CLI turn only (the manual one through the window, where the model wrote `shop.orders`).
- **A Production-labelled connection gets a warning, nothing stronger**: one line in the access popover when rows are allowed, one in the review dialog. Neither has an automated test.
- **The activity log is a local convenience record.** It lives in `puricat.db` (mode 0600 on Unix) in clear text apart from masked password literals — the mask is the history's heuristic, with its limits ("SQL console"). It keeps the newest 5,000 entries, can be cleared by the user, is not deleted with a connection, and a failure to write it does not stop the action. Entries for reads and proposals are written when their turn ends. Catalogue lookups are not logged. The refusal of an approved proposal on a read-only connection is not logged.
- **Tool results stay in the conversation**, in web view memory, until "New chat" or the app closes.
- **Unix only.** The socket and the bridge need Unix domain sockets; on other platforms a turn with tools fails with a message. Nothing was run there.
- **Backend text is English in every UI language**: the reason a step failed, the note on a flagged statement, the detail line of a log entry.

### Still planned (Phase 5)

- A policy per connection for what the AI may do, in place of one global level; a stricter step for Production-labelled connections.

## Backups

How it is built is in [ADR 0021](docs/adr/0021-backups-with-dump-tools.md); what a backup holds and how to restore one is in [BACKUP_RESTORE.md](BACKUP_RESTORE.md).

**The dump tools are the user's own installations.** PuriCat runs whichever `mysqldump`, `mariadb-dump` or `pg_dump` it finds in `PATH`, in Homebrew's directories, in Postgres.app or in the vendors' installer locations, and does not verify its origin. That program receives the password and reads the whole database. This is the same trust as for the AI CLIs.

**The password is never an argument.**

- `mysqldump` reads it from an option file: created with mode 0600 inside a directory of mode 0700 with a random name under the temporary directory, removed when the run ends, also after a failure. It is given with `--defaults-file`, which replaces the user's own option files: nothing in `~/.my.cnf` can redirect the dump to another server. A password with a line break is refused, since the file could not hold it.
- `pg_dump` gets it in `PGPASSWORD`. Its environment is cleared and rebuilt (`PATH`, `HOME`, the TLS settings): the user's own `PG*` variables do not reach it. Another process of the same user can read a process's environment; such a process is outside the threat model.
- The tools' error output is shown to the user and stored in the history. The tests check that a refused password is not in it.

**What is on disk afterwards.**

- The backup file, mode 0600, in the folder the user chose. **It is not encrypted**: it holds the database's data in clear, and whoever can read the folder can read it. A folder that syncs to a cloud service sends it there.
- A file is written as `.<name>.partial` and renamed only after it was checked. A failed or stopped run removes it.
- The history (`backup_runs`): connection name, database, time, tool, size, the file's path, the reason of a failure. No data from the database.

**The folder is a path the web view names.** The dialog for choosing it is shown by the backend, but the chosen path comes back from the web view with `run_backup` and `save_backup_job`. The backend requires an absolute path and creates the folder; it does not confine where that is. A script in the web view could therefore have a backup written to any folder the user can write to. It cannot read one: `reveal_backup` takes the number of a run in the history, shows that run's file in Finder and nothing else.

**Scheduled backups install a LaunchAgent.**

- A per-user agent, `~/Library/LaunchAgents/com.purivaro.puricat.backups.plist`: no privilege, no daemon. It is written and loaded when a schedule is saved, and removed with the last schedule. The dialog says so before the schedule is saved. macOS reports it as a background item.
- It starts PuriCat's own executable with `--run-backups --data-dir <the settings folder>`. In that mode the executable opens no window; it reads the jobs from the settings database, each connection's password from the Keychain, runs what is due and ends. One runs at a time (a lock file).
- The paths in the property list are escaped as XML text; `launchctl`, `open` and `osascript` are started with fixed argument vectors. The texts of a failure notification are arguments of the AppleScript, never part of it.
- **A scheduled backup runs with nobody watching.** It uses whatever dump tool is found at that moment, and whatever the connection's profile says at that moment.

**Deleting.** Only files recorded in the history as made by a schedule are ever deleted, only beyond the number to keep, and only after a newer backup was kept. A backup made by hand is never deleted.

**A restore creates a database and replaces nothing** ([ADR 0022](docs/adr/0022-restore-into-a-new-database.md)).

- The only target is a database that `restore_backup` creates itself, with a `CREATE DATABASE` that has no `IF NOT EXISTS`. A name that is taken is refused by PuriCat and, were that check skipped, by the server. No command of this feature drops, truncates or replaces anything, also after a failure.
- **The web view names a run of the history and a new name; it never names a file.** The backend loads only the file that run recorded, only for the connection the run belongs to, and only while the file has the size that was recorded. A script in the web view can therefore create databases on a connection that is open and not read-only, filled from that connection's own backups; it cannot load anything else.
- **The size is not a signature.** No checksum of a backup is stored. Whoever can write to the backup folder can change a backup, keep its size and its closing line, and have its SQL run with the connection's rights at the next restore — into the new database, but a dump is a script: it can name other databases the account may write to. The folder is as trusted as the connection.
- The client is the one installed next to the dump tool, started as the dump tool is: a fixed argument vector, no shell, a cleared environment, the password in MySQL's private option file or in `PGPASSWORD`. Its error output is shown to the user; the tests check that a refused password is not in it.
- After a failed or stopped load PostgreSQL's new database is empty (one transaction); MySQL's holds what was loaded up to then. The message says which, and that the database is still there. PuriCat does not drop it.
- A read-only connection cannot restore. A Production-labelled one gets a warning and a danger-styled button, as for a new database; there is no typed confirmation, because nothing existing is at stake.

Not done: encryption of backup files; a restore over an existing database and its confirmations; a checksum of a backup; a record of restores; confining the folder; a time limit for a scheduled run; a check of the dump tool's origin.

## App updates

How it is built is in [ADR 0020](docs/adr/0020-in-app-updates.md); what was tested is in [TESTING.md](TESTING.md).

**What leaves the machine.** A check is one `GET` of `https://github.com/purivaro/PuriCat/releases/latest/download/latest.json`, and an install is one `GET` of the package that manifest names. The address has no variable part and no query. The headers are `Accept`, `Host` and `User-Agent: tauri-plugin-updater/<its version>`: no PuriCat version, no identifier, no cookie, nothing about connections or databases. GitHub sees the IP address and the time. This is the only request PuriCat's own code makes that is not to a database the user connected. The end-to-end tests log every request the app makes to a stand-in server and fail on any other method, path or header.

**When.** Once at start-up unless the switch "Check when PuriCat starts" (in the update dialog) is off, and whenever the user asks. Nothing is downloaded until the user chooses "Download and install".

**What is installed.**

- Only a package that carries a minisign signature made with the release key, whose public half is compiled into the app from `src-tauri/tauri.conf.json`.
- The signature must also name the version the manifest announced (`requireSignedVersion`). The manifest itself is not signed: without this, whoever can answer the request could offer an old, genuinely signed release under a higher number.
- The manifest is fetched over HTTPS only in release builds. The install does not rest on that: a changed package, a relabelled one and one signed with another key are refused whatever the transport, and the app on disk is left byte for byte as it was (tested against a stand-in server over plain HTTP).
- `install_update` takes no argument from the web view. It installs what the backend's last check found.
- The process must run from an app bundle (`…/PuriCat.app/Contents/MacOS/…`); otherwise the install is refused before any download, because the updater would replace the directory the executable is in.

**The web view gained no permission.** The updater plugin is registered, but none of its permissions is in the capability file; the web view reaches it through `check_update`, `install_update` and `restart_app` only. The Content-Security-Policy is unchanged: the requests are made by the backend.

**A restart is the user's step.** Installing replaces the app on disk and nothing else. "Restart now" is separate, and says how many tabs hold staged edits, an open transaction or an unsaved script before it discards them.

**The release key.**

- The private key is a repository secret (`TAURI_SIGNING_PRIVATE_KEY`, with `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`), used by the release workflow only, and a copy the owner keeps. It is not Apple's signing key: the package also holds the Developer ID signed and notarized app, which the workflow checks after unpacking it.
- If the key leaks, its holder still needs to answer the manifest request (GitHub's answer, or the user's network together with a certificate the system trusts) to install their own program. If it is lost, installed apps cannot be updated by the app any more: a new key means a manual download once.
- An installed app trusts the key it was built with, for good. There is no way to rotate it from afar.

Not done: the manifest is not signed (the signed version closes the gap that matters); there is no pinning of GitHub's certificate; the package is not checked against Apple's notarization at install time (Gatekeeper does not look at an app that replaces itself; the signature above is the check); the app does not look again while it stays open.

## Debug-only test hooks

| Variable | Effect |
|---|---|
| `PURICAT_DATA_DIR` | Use this directory instead of the app-data directory |
| `PURICAT_SECRET_STORE=memory` | Keep passwords in process memory instead of the OS credential store |
| `PURICAT_E2E_SCRIPT` | Evaluate this file in the web view after each page load |
| `PURICAT_E2E_REPORT` | File that the `e2e_report` command writes |
| `PURICAT_E2E_PICK` | A list of paths (separated by `:`). Each request for the Open dialog is answered with the next one instead of showing the dialog; after the last, as if it was cancelled |
| `PURICAT_BACKUP_AGENT=1` | Lets a debug build install the LaunchAgent for scheduled backups, under a label of its own (`com.purivaro.puricat.backups.dev`). Without it a debug build installs nothing and says that schedules do not run |
| `PURICAT_UPDATE_ENDPOINT` | The address of the update manifest. A debug build asks only this address, plain HTTP included, and refuses to check without it: it never asks GitHub. The public key and the signature checks are the same as in a release build |

`PURICAT_E2E_PICK` also answers the Open dialog of the SQLite connection form and the one of "Open SQL file…".

They exist so tests never touch real settings or the Keychain ([ADR 0012](docs/adr/0012-e2e-testing-on-macos.md)). All seven are behind `#[cfg(debug_assertions)]` and are absent from release builds. With `PURICAT_E2E_SCRIPT` set, the window is also kept on top of other windows, because a covered web view pauses its timers. The `e2e_report` command remains registered in release builds but only returns an error. Debug builds must not be distributed.

One hook is not debug-only: a query tab attaches its Monaco editor object to the tab's root DOM element as `__editor`, in every build, so the end-to-end test can set the editor's text. Since 2026-11-20 the view form does the same on its `<form>` element. It gives a script that already runs in the web view nothing it could not reach otherwise.
