# PuriCat requirements

This is a condensed restatement of the product brief. The source of truth is [docs/PuriCat_Master_Requirements.md](docs/PuriCat_Master_Requirements.md); if the two disagree, the brief wins.

Status values: **Done** (implemented and verified), **Partial** (some of it is implemented; the note says what), **Planned (Phase N)** (not in the code). Evidence for "Done" is in [TESTING.md](TESTING.md). Status as of 2026-11-16.

## Confirmed product decisions

- macOS first (Apple Silicon), Windows later; platform abstractions stay portable.
- Replace Navicat for routine work, delivered in phases.
- Two editing paths: direct paste into an editable grid with staged changes, and a guided Insert / Update / Upsert wizard.
- AI agent through locally installed Claude Code and Codex CLIs, using documented interfaces only. Every AI-initiated mutation needs explicit approval.
- Ordinary row edits commit on Save; bulk changes and AI mutations need preview and confirmation, configurable per connection and stricter for production.
- Public distribution: secure defaults, no hard-coded paths, accounts or private infrastructure.
- SSH tunnels, several simultaneous connections, light and dark themes, PostgreSQL, scheduled backups, English and Thai.

## 4. Table editing (flagship)

| Requirement | Acceptance criteria | Status |
|---|---|---|
| Editable grid with staged changes, undo/redo, Save / Discard | Paste creates pending edits only; nothing reaches the server before Save | Done for MySQL and PostgreSQL tables with a primary key: in-cell editing, single-range selection, add / delete / restore rows, undo / redo, Save / Discard, unsaved-edit guards. Edits are limited to the loaded page. Not editable yet: generated, binary and MySQL spatial columns, cells truncated for preview, rows whose key is NULL or truncated. Automation uses synthetic events; native keyboard, IME and drag input are untested. Multi-range selection, a full-value editor, filtering and editing across pages are Planned (Phase 3) |
| Clipboard parser (TSV/CSV, quotes, embedded tabs/newlines, Thai, NULL vs empty, precision) | Unit-tested round trips | Partial: TSV as written by Excel / Google Sheets / Numbers is done and unit-tested (quoted cells, embedded tabs and line breaks, doubled quotes, ragged rows, Unicode, no reinterpretation of numbers or dates). Empty text becomes NULL only in nullable non-text columns. Smart Paste reads the same TSV clipboard format. CSV (and CSV / XLSX files) is Planned (Phase 4, import) |
| Direct paste into the grid | A copied cell fills the selection; a block pastes from the top-left; overflow is reported | Done: rows past the end become new rows; columns past the right edge and read-only cells are skipped and reported |
| Smart Paste: INSERT, UPDATE and UPSERT modes | INSERT adds every row (optionally refusing rows whose key already exists); UPDATE changes existing rows and never inserts; UPSERT does both | Done for MySQL and PostgreSQL in the backend (live tests, all three modes). Through the UI only UPSERT on MySQL is verified (E2E); INSERT and UPDATE modes and PostgreSQL through the UI are not yet verified. Offered on editable table tabs only (a table with a primary key, a writable connection, no unsaved edits) |
| Smart Paste: read the clipboard, choose headers, map columns, choose key and update fields | Excel / Google Sheets clipboard; first row as headers or data; map and skip columns; choose the matching key and the columns to update | Partial: done — clipboard TSV, header-row detection with a manual override, mapping by header name or by position with per-column skip (a table column receives at most one pasted column), key choice among the usable unique keys (UPDATE and UPSERT always use one — the first usable key unless another is picked — also after "no key" was chosen in INSERT mode; the mode switch has no automated test), per-column "Update" switch, an option to read the text `NULL` as NULL, empty rows ignored and counted. Not done: a side-by-side preview of source and destination rows (the mapping list shows one sample value per pasted column) |
| Smart Paste: key matching | UPDATE / UPSERT use a primary key or a validated unique key, including composite keys; ambiguous matching refused; duplicate keys in the paste detected | Partial: done and verified in the backend for single-column and composite keys (live tests on both engines) — the key must be the primary key or a plain unique index read from the catalogue (prefix, expression and partial unique indexes are excluded), must be fully mapped, and is validated again in the backend; pasted rows with the same key are reported as duplicates, both as exact text and as the database compares them (collation, numeric spelling), also when the two spellings fall into different 40-row lookups (unit-tested). Not yet verified: composite keys through the UI. A table with only a unique index (no primary key) cannot open the wizard |
| Smart Paste: show type and constraint errors, unmatched and duplicate rows | Problems are visible per row before anything runs | Partial: one status per pasted row (insert, update with the changed columns, unchanged, unmatched, missing key, duplicate, exists, invalid) plus counts. Pre-checks cover number-looking text for numeric columns, the declared length of `char` / `varchar`, NULL into NOT NULL, and required columns that are not mapped. Everything else (dates, enums, foreign keys, other unique indexes) is judged by the server at run time and rolls the run back. Pasted key values get the same checks and, for an integer key column, must be whole numbers (`12abc`, `1.9`, `1e2` are invalid rows and are never sent to the database; unit and live tests); key values of other types that the database coerces, such as dates, are not pre-validated beyond that ([DATABASE_COMPATIBILITY.md](DATABASE_COMPATIBILITY.md), Smart Paste). Rows with problems block the run; a "skip invalid rows" option is Planned (Phase 3) |
| Smart Paste: engine semantics and safe strategy | Semantics explained; no blind `MERGE`; parameterised, transactional, with concurrency checks | Done for MySQL and PostgreSQL: PuriCat matches on the chosen key itself and runs plain parameterised INSERT and UPDATE statements; no `ON DUPLICATE KEY UPDATE`, `ON CONFLICT` or `MERGE`; the dialog says so ([ADR 0014](docs/adr/0014-smart-paste-match-then-write.md)). UPDATEs carry the optimistic check on the values seen by the analysis made at run time. SQL Server is Planned |
| Smart Paste: respect generated columns, defaults, constraints, collations, decimals | Server-generated values, defaults and the engine's comparison rules are honoured | Partial: generated key columns can be used to match but are never written (with one in UPSERT mode, a blank key is a new row and an unknown key is skipped, not inserted; in INSERT mode an unknown key is an invalid row and a blank key inserts). Unmapped columns take their defaults; a NULL for a NOT NULL column with a default is left out of the INSERT so the default applies (backend, verified). The wizard sends an empty cell of any non-text column as NULL, also a NOT NULL one, so an empty cell reaches that path (request building unit-tested; not exercised end to end); an empty cell of a text column stays an empty string. Key equality is decided by the database (collation and type rules). Decimals are sent as the exact pasted text, but "update" compares text, so `1.5` against a stored `1.500000` counts as an update (value-aware comparison is Planned, Phase 3). Foreign keys and time zones are left to the server as on the save path |
| Smart Paste: preview counts and plan; bounded batches with progress, cancellation and rollback | Exact insert / update / skip / conflict counts; operation plan; progress; cancel | Partial: the preview is read-only and gives exact counts and the per-row operation plan (the SQL text is not shown). At run time the table is analysed again and nothing runs unless every row's outcome is the approved one: the preview carries a fingerprint of each row's status and changed columns, and the run must reproduce it (verified, including an outcome with the same counts but different rows). **One transaction, not several batches**: at most 10,000 pasted rows, one statement per row, each required to affect exactly one row; progress every 20 statements; "Stop and roll back" and any error undo everything. Chosen for atomicity; multi-batch and streamed imports are Planned (Phase 4, import). Progress and Stop are verified in the backend only. While a run is in progress the dialog cannot be dismissed (Esc, outside click and the close button are blocked; "Stop and roll back" is the way out) — implemented, not yet verified by an automated test |
| Smart Paste: error reporting | Affected and failed rows, recoverability, whether the transaction rolled back | Partial: a failure names the row (its key, or "new row"), carries the server's message and states that nothing was saved. Only the first failing row is reported; there is no list of all failing rows |
| Safe execution | Parameterized values, quoted identifiers, bounded batches, transactions, optimistic concurrency, no edits on keyless tables | Partial: parameterised values, quoted identifiers, complete-primary-key addressing, one transaction per save, exactly-one-row rule, optimistic concurrency on edited columns, at most 10,000 row changes per save; verified by live tests on both engines. Keyless tables are read-only in the UI (the backend would allow INSERT only). DELETE checks the key only, not the row's contents. Smart Paste runs use the same planner and add progress and cancellation; grid saves have neither. Execution in several batches is Planned (Phase 4, import) |
| Bulk and production safeguards | Review step and configurable impact thresholds | Partial: a review dialog shows the exact statements and bound values; it is mandatory for Production-labelled connections, for any delete, and above the per-connection threshold (`bulkReviewRows`, default 10). Only the delete-triggered path is verified end to end. Smart Paste never runs without a current preview (Run is disabled until the preview matches the set-up, and the backend re-checks the approved outcome row by row); on a Production-labelled connection it shows a warning and a danger-styled Run button, with no typed confirmation and no row threshold. An audit log of saves is Planned (Phase 3) |

| Risk-based confirmation for dangerous scripts | Not keyword matching alone | Partial. The guard is verified on both engines (live tests) and through the UI on MySQL (E2E); the confirmation through the UI for a `DELETE` without `WHERE` (E2E, cancelled); the Production path has no automated test. | Import with mapping and error reports | Batch import with cancellation | Partial: a CSV / TSV file or an Excel / OpenDocument workbook of up to 10,000 data rows opens in Smart Paste, with its mapping, preview, single transaction and "Stop and roll back". ## 6. AI agent

| Requirement | Acceptance criteria | Status |
|---|---|---|
| Detect Claude Code and Codex CLIs, version and sign-in state | Missing prerequisites explained; no account details kept | Done |
| Agent conversation with schema context | Streamed responses through a documented CLI interface | Partial ([ADR 0016](docs/adr/0016-agent-chat-without-tools.md)). Done: a chat in the AI panel through the user's Claude Code or Codex CLI — one process per turn, fixed arguments, the prompt on stdin, an empty working directory, Stop, a 10-minute timeout; provider switch and model selector ("Default model", the CLI's models, any name); the schema of the tab in front as context (40 tables with columns, the rest by name) plus the active query tab's SQL; answers rendered from Markdown as text; "Try again" and "New chat". By default the model has no tools: it cannot look anything up or run anything (the database tools of the next row are off unless the user turns them on). Verified for Claude Code (unit tests on lines captured from the real CLI, E2E on stand-in CLIs in dev mode and against the bundled app, repeated on the build with the database tools; an opt-in test against the real CLI). **Codex's successful path is not verified against the real CLI** (only the service's refusal was observed; Claude streams text as it is written, Codex delivers whole messages). Not done: a saved or exportable conversation, several conversations, schema context beyond the first 40 tables or with foreign keys, CLI version checks. Backend messages are English only |
| Read-only tools by default; mutations only after approval | Approval shows SQL, target, impact estimate; outcome logged | Partial ([ADR 0017](docs/adr/0017-ai-database-tools.md)); done for Claude Code. The tools are **off** by default, which is stricter than the requirement: the user chooses "Structure" (list schemas and tables, describe a table) or "Structure and rows" (also one read-only query at a time, 50 rows by default and 200 at most, as a single statement in a read-only transaction that is rolled back), for the database of the tab in front. PuriCat serves the tools itself, as an MCP server on a Unix socket that lives for one turn and that the CLI reaches through PuriCat's own executable; the model gets no tool that writes. A mutation is a proposal: a card with the SQL, then a review dialog with the whole SQL, the connection, its environment and database, the flagged statements and what guards the run; PuriCat runs it only after "Approve and run", with the SQL console's impact guard, and a read-only connection refuses it. Outcomes are logged: a local activity log records every row-reading query, refused or failed read, proposal, approval, rejection and outcome, with password literals masked. Verified: unit tests; live tests on MySQL and PostgreSQL (18 and 20 write attempts through the reading tool refused, the data unchanged); E2E through the UI with a stand-in CLI that is a real MCP client — on PostgreSQL at "Structure and rows" (approve, rolled back by the row limit, run without the limit, reject, the log) and on MySQL at "Structure" (no query tool offered, the structure the model was given, one approved proposal); an opt-in test with the real Claude Code CLI below the UI; and one turn of the real Claude Code CLI through the window, driven by hand once on PostgreSQL (two read-only queries, a proposal approved in the review dialog, the log) — not an automated test. Against the acceptance criteria: the approval shows the SQL and the target; **it shows no impact estimate** — the impact is measured by the guard when the statement runs, and a statement above the connection's row threshold is rolled back and asked about again. Not verified: **any Codex turn with tools** (handshake only); what a turn of the real Claude Code CLI with tools has available besides PuriCat's tools; a query tab in front, rows on MySQL and the "Structure" level on PostgreSQL through the UI; the Production warning; the read-only refusal; Stop of a running proposal. Unix only. Not done: a per-connection policy, redaction of what the tools return ([SECURITY.md](SECURITY.md), AI database tools) |
| Context preview and redaction | User sees and controls what is shared; secrets never sent | Partial. Done: the context is produced by the backend as names and types only — no rows, column defaults, hosts, ports, user names, passwords or connection name; a context inspector shows it for the tab in front; every sent message keeps the exact context that went with it; one switch turns sharing off (unit test of the text; E2E for the inspector and for the prompt the CLI receives; the switch and the per-message record have no automated test). With the database tools on, a second control decides what the model may fetch itself — nothing, the structure, or the structure and rows — and every tool call is shown in the answer as a step that opens to the exact text the model was given (E2E: a query step on PostgreSQL, a `describe_table` step on MySQL). Not done: marking columns as sensitive, redaction of the context or of tool results, sample rows chosen by the user, pinning, narrowing the scope. The SQL of the active query tab is sent as typed apart from masked password literals, rows read by the tools are sent as the database returned them, cut for length only, and schema names can themselves be sensitive ([SECURITY.md](SECURITY.md), AI chat and AI database tools) |
| No fabricated responses | No chat UI until it is backed by a real integration | Done: the chat shows only what the CLI printed; a failure is shown in the CLI's own words; without an installed, signed-in CLI there is no chat, only what is missing |

## Definition of done for the first public macOS beta

From the brief: a new user can install PuriCat, create SSH/TLS-enabled connections to MySQL, SQL Server and PostgreSQL, browse several databases at once, open large tables, edit and paste from Excel in both modes, review and commit safely, run SQL and export results, use an installed Claude Code or Codex CLI to propose SQL with explicit mutation approval, configure manual and scheduled backups with accurate status, switch themes, and understand every limitation from the UI and docs. All of it verified against disposable test databases.

Current distance from that bar is tracked in [ROADMAP.md](ROADMAP.md).
