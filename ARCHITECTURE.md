# Architecture

Describes the code as it exists on 2026-11-16. Planned pieces are marked as such. Decisions and their trade-offs are in [docs/adr/](docs/adr/README.md).

## Components

```
|                                                                        |
|  Web view (WKWebView)                 Rust                             |

|                                       |  model    store    secrets  |  |
|                                       |  db (adapters, write, smart,|  |
|                                       |     console, script, export,|  |
|                                       |     ddl, users)             |  |
|                                       |  ai_detect    agent         |  |
|                                       |  agent_tools  mcp           |  |
|                                       +--+-------+-------+-------+--+  |
+------------------------------------------|-------|-------|-------|-----+
                                           |       |       |       |
                                  puricat.db   OS credential   MySQL /      claude / codex
                                  (SQLite,     store           PostgreSQL   (status commands;
                                  app data)    (Keychain)      servers      one process per
                                                                            chat turn)
                                                                               |  only in a turn with
                                                                               v  the database tools on
                                                              puricat --mcp-bridge <socket>

                                                               back to a Unix socket of the
                                                               running app: `mcp`)
```

The backend also writes export files (CSV, JSON, XLSX) to paths the user picks in the native Save dialog. The `claude` and `codex` processes are the only part that talks to an AI provider. By default they are given text on stdin and no database access ([ADR 0016](docs/adr/0016-agent-chat-without-tools.md)). When the user has turned the database tools on, the CLI of that turn can also call tools that the running app serves on a Unix socket; the CLI reaches the socket by starting PuriCat's own executable in bridge mode, and the database connection stays in the app ([ADR 0017](docs/adr/0017-ai-database-tools.md)).

| Component | Responsibility | Must not |
|---|---|---|
| `src/` (React) | Rendering, interaction, view state, staged edits, Smart Paste set-up (mapping, mode, key), the SQL editor and the confirmation before a risky script, the "New database" form, the forms of the database menu — edit, drop, flush — those of the table menu — definition, rename, empty, drop — and the view form (the choices, the view's query as the user typed it, and the statements the backend returns for them), the users dialog (the accounts of a server, what one may do, and the forms for a new user, another password and a drop: the choices, a password typed or generated there, and the statements the backend returns, masked unless the user asks to see the password), the agent chat (the conversation, which context to ask for, the access level of the database tools and the scope a turn's tools are bound to, rendering answers with their tool steps and proposal cards, the review dialog, the activity log) | Hold stored passwords, build SQL (text typed in a query tab is passed to the backend unchanged; it is split, classified and run there — and so is the query typed in the view form, which the backend checks and writes `CREATE VIEW … AS` around; the users dialog sends choices and the password, and the backend writes every statement), touch files or processes, run SQL from an AI answer (it can only be placed in a query tab's editor), send the SQL of a proposal back to be run (it sends the proposal's id; the backend runs its own copy) |
| `src-tauri` (`puricat`) | IPC commands, open sessions, one console per query tab and per running proposal, cancel flags of running jobs (Smart Paste runs and agent turns), the AI's undecided proposals, writing the AI activity log, the location of the AI CLIs' scratch directory, choice of secret store, clipboard and dialog plugin registration, debug-only test hooks. Its `main` also has the bridge mode: started with `--mcp-bridge <socket>` it calls `puricat_core::mcp::bridge` and nothing else | Contain database or storage logic |
| `crates/core` (`puricat-core`) | Profiles, settings store, SQL history and AI activity log, secrets, adapters, the SQL console, export writers, CLI discovery, the agent chat runner (prompt, context text, CLI process, stream parsing), the AI's database tools and the MCP server and relay that serve them | Depend on Tauri |

`puricat-core` has no Tauri dependency so it can be unit-tested without a window and reused by the planned backup helper ([ADR 0002](docs/adr/0002-core-crate-and-thin-ipc.md)). That record also expected the MCP server to run outside the desktop process. It does not: the server runs inside the app, and the relay a CLI starts to reach it is a mode of the app's own executable, not a separate binary.

## Core modules

| Module | Contents |
|---|---|
| `model` | `ConnectionProfile`, `Engine` (`mysql`, `postgres`, `sqlite`, `sqlserver` — the last has no adapter). A SQLite profile is a `file` path; host, port, user name, default database and TLS are cleared, `Environment`, `TlsMode`; input normalisation |
| `store` | SQLite settings database: `connections` (one JSON profile per row plus timestamps), `settings` (key/value), since migration 2 `query_history` (one row per run of a query tab; at most 1,000 rows are kept) and, since migration 3, `agent_audit` (the AI activity log: time, connection id and name, database, provider, model, event, SQL, detail; `add_audit` keeps the newest 5,000 rows, `list_audit` returns at most 1,000 newest first, `clear_audit` deletes all) and, since migration 4, `saved_scripts` (the user's saved scripts: connection id, name, text, created and updated times; a name is unique per connection without regard to ASCII case, at most 120 characters and one line; the text is stored as written, at most 1 MB). Append-only migrations keyed on `PRAGMA user_version`; a database from a newer build is refused |
| `secrets` | `SecretStore` trait; `OsKeychain` (via `keyring`) and `MemoryStore` (tests, debug runs). Service `PuriCat`, key `connection/<id>/password` |
| `backup` | Backups with the vendors' dump tools ([ADR 0021](docs/adr/0021-backups-with-dump-tools.md)): finding the tools and reading their versions, choosing one for a server, the argument vectors and the option file, one run (`run`) from the partial file to the checked and renamed one |
| `backup_schedule` | `Schedule` (off, daily, weekly) with its previous and next time and launchd's calendar entries; `is_due`; which scheduled backups are beyond the number to keep; `perform` (one backup written into the history, then retention) and `run_due` (every job that is due), used by the app and by the runner |
| `db` | `Session` enum (`MySql`, `Postgres`, `Sqlite`), `Capabilities`, shared paging/truncation logic, `ident` quoting, one module of SQL per engine. `db::sqlite` opens a file (existing files only, read-only when asked, nothing of the file's settings changed), reads the catalogue from `sqlite_master` and the `pragma_…` table functions, and maps declared types to an affinity and a value kind ([ADR 0018](docs/adr/0018-sqlite-files.md)) |
| `db::filter` | Turns the conditions of a table tab's filter into one parameterised `WHERE` clause: a fixed set of operators (comparisons, text searches, NULL tests, a list of values, a range, the empty text), the column checked against the table's metadata, typed comparison for numbers, dates and text, the shown text for everything else; the conditions joined with `AND`, or with `OR` when the request says `matchAny`; at most 20 conditions, 200 values in a list and 1,000 bound values ([DATABASE_COMPATIBILITY.md](DATABASE_COMPATIBILITY.md), "Row filter") |
| `db::write` | Turns a change set (updates, inserts, deletes) into parameterised statements and enforces the write rules; the engine modules execute the plan in one transaction ([ADR 0013](docs/adr/0013-staged-edits-and-optimistic-saves.md)) |
| `db::smart` | Smart Paste ([ADR 0014](docs/adr/0014-smart-paste-match-then-write.md)). `Draft` holds the pure logic: validation of the set-up against the table metadata and its unique keys, duplicate detection, the lookup queries to run, classification of every pasted row and the resulting change set. It performs no I/O; `Session` supplies the catalogue data, runs the lookups it asks for and feeds the results back |
| `db::ddl` | Schema changes made through a form ([ADR 0019](docs/adr/0019-schema-changes-through-forms.md)); today the forms for a database and the menu of a table or a view. `create_database` turns a `NewDatabase` (name; character set and collation for MySQL; owner, template and encoding for PostgreSQL) into the one `CREATE DATABASE` statement for the engine: names through `ident`, the keywords that are not identifiers (character set, collation, encoding) through a strict pattern, an option of the other engine refused, SQLite and SQL Server refused. Pure functions, no I/O: `Session::create_database_sql` returns the text for the form's preview, `Session::create_database` calls the same function and runs the text (`execute_statement` in the engine modules), and `Session::database_options` reads what the server offers for the form's lists (`DatabaseOptions`). `alter_database` turns an `AlterDatabase` (the name as it is now; `charset?`, `collation?` for MySQL; `newName?`, `owner?` for PostgreSQL) into the `ALTER DATABASE` statements as a list, in the order they run — one on MySQL, the owner before the rename on PostgreSQL — and refuses an empty change, the same name again, and a new PostgreSQL name over 63 bytes. `drop_database` returns the one `DROP DATABASE`. Both refuse the server's own databases (`is_protected`). `flush` maps a `Flush` kind (`privileges`, `tables`, `logs`, `status`) to one of four constant MySQL statements. `Session` adds what needs the connection: `database_details` (what a database is set to now, and a best-effort count of its tables and views), the `…_sql` functions for the previews, which also refuse a drop or a rename of the database a PostgreSQL session is opened on, and `alter_database` / `drop_database` / `flush`, which run what the same builders return. On PostgreSQL the alter statements are joined into one simple query, and before an alter or a drop `PgSession::release` closes the session's own pool for that database. **The table menu.** `table_change` turns a `TableChange` — `rename` (`table`, `kind`, `newName`), `empty` (`table`) or `drop` (`table`, `kind`), where `kind` is the `ObjectKind` `table`, `view` or `matview` — into one statement for MySQL, PostgreSQL or SQLite: the table addressed with its database (MySQL), its schema (PostgreSQL) or alone (SQLite), every name through `ident`, no `IF EXISTS` and no `CASCADE`; it refuses an empty, unchanged or over-long new name, a PostgreSQL table without a schema, a materialized view on another engine, a rename of a SQLite view, and SQL Server. `Session::table_change_sql` returns that text for the preview and `Session::table_change` runs it: `execute_statement` on MySQL, `PgSession::execute_on` on the database that holds the table (not `home`), and `SqliteSession::execute_statement` on the file's writable handle, which refuses a file opened read-only. `Session::table_definition` reads, and returns a `Definition`: the `sql` and its `source` — `server` (MySQL's `SHOW CREATE`), `file` (SQLite's `sqlite_master`, with the table's indexes and triggers) or `catalogue` (PostgreSQL: `pg_get_viewdef` for a view; for a table, text assembled in `PgSession::table_definition` from `pg_attribute`, `pg_constraint`, `pg_index`, `pg_trigger` and the comments). **The view form** (ADR 0019, section 9). A `ViewSpec` is a `TableRef` (where the view is, and its name), `select` (the view's query only: what follows `AS`) and `replace` (the view exists). `view_query` checks the query — not empty, `script::single_read`, and a first word of `SELECT`, `WITH`, `VALUES` or `TABLE` — and returns it without its final semicolon; it is the one place where a form's text reaches a statement as SQL. `view_statements` returns the statements in the order they run: `CREATE VIEW <name> AS`, a line break and the query; for `replace`, `CREATE OR REPLACE VIEW …` on MySQL and PostgreSQL, and on SQLite `DROP VIEW <name>` followed by the `CREATE VIEW`. A new name is trimmed and length-checked, the name of a view that exists is taken as it is; SQL Server is refused. `Session::view_statements_sql` returns them for the preview and `Session::save_view` runs them: `MySqlSession::execute_in` (a connection detached from the pool, `USE <database>`, the statement, the connection closed), `PgSession::execute_on` on the view's database, or `SqliteSession::execute_all` (every statement in one transaction on the writable handle, which refuses a file opened read-only). `Session::view_select` reads the query of a view as it is kept — `information_schema.VIEWS.VIEW_DEFINITION` (MySQL), `pg_get_viewdef` for an object of kind `v` (PostgreSQL), `script::view_query` on the statement in `sqlite_master` (SQLite). `Session::preview_select` tries a query: `view_query`, then `open_reader` on the view's database and `Console::read_only` with the row limit it is given, cancelled through the console's `Canceller` after `PREVIEW_TIMEOUT` (15 seconds); it returns a `QueryPreview`, the console's `ResultPreview` with `elapsedMs` |
| `db::users` | The accounts of a server and the forms of the users dialog ([ADR 0023](docs/adr/0023-users-from-templates.md)), on MySQL and PostgreSQL; SQLite and SQL Server are refused. Pure builders, no I/O: `create_user` turns a `UserSpec` — `account` (`name`, and on MySQL `host`, `%` when left out), `template` (`app`, `readOnly`, `none`), `database?`, `password` — into the statements in the order they run, each a `Step` with its `sql` and, on PostgreSQL, the `database` it runs inside (`None`: the session's own database — roles and database privileges belong to the whole server); `change_password` and `drop_user` return one statement each. What the text depends on is passed in as `Facts`: MySQL's `NO_BACKSLASH_ESCAPES` and `partial_revokes`, PostgreSQL's `standard_conforming_strings` and the schemas of the target database that are not the server's own. `Show` says what stands where the password goes: `Run` (the literal), `Masked` (`MASK`, `'••••••••'`; an empty password allowed) or `Revealed`. The quoting rules — names and hosts as string literals with a backslash refused, the password written for the session's mode, `_` and `%` escaped in a grant's database — are in the module's own comment and in [SECURITY.md](SECURITY.md), "Users and privileges". `is_system` names the server's own accounts (`mysql.…`, `pg_…`), `display_name` writes an account as the drop form asks for it (`user@host` on MySQL), and `without_password` takes the password out of a server's message. `Session` adds the I/O: `list_accounts` (`mysql.user`; `pg_roles` without the `pg_…` roles, those that can log in first, with the session's own marked through `CURRENT_USER()` / `current_user`), `account_details` (MySQL: plugin and password expiry from `mysql.user`, and `MySqlSession::show_grants`; PostgreSQL: the attributes from `pg_roles`, memberships from `pg_auth_members`, and per database `has_database_privilege`), `plan_user` / `plan_password` / `plan_drop_user`, which read the facts and return the text, and `create_user` / `change_password` / `drop_user`, which run it. `refuse_untouchable` turns away the server's own accounts, the session's own and a PostgreSQL superuser, for a password change and a drop. On MySQL `MySqlSession::account_connection` takes a connection out of the pool and reads `@@SESSION.sql_mode` and `partial_revokes` on it (`account_facts`); a creation and a password change are built for what it read and run on it, and it is closed afterwards; a drop runs on the pool. On PostgreSQL the role and its `CONNECT` go as one simple query on `home` and the statements inside the target database as another on that database's pool, each one implicit transaction. When a step after the first fails, the creation is undone — `DROP USER` on the same MySQL connection, `REVOKE ALL PRIVILEGES ON DATABASE …; DROP ROLE …` on PostgreSQL — and the error says so |
| `db::script` | Reads SQL text without parsing it: a dialect-aware scanner (strings, comments, MySQL backticks, PostgreSQL dollar quotes) that splits a script into statements, classifies each as `read` / `dml` / `ddl` / `transaction` / `other` with an optional "danger" reason, says whether a transaction-control statement leaves a transaction open, says whether a statement mentions a keyword outside strings and comments (`mentions`, used for `TEMPORARY`), and masks password literals in single or double quotes for the history and the AI activity log. `single_read` is the text check of the AI's query tool, and since 2026-11-20 of the view form's query: it returns the one statement of a text if that statement only reads — exactly one statement, a reading kind, no `INTO`, no locking clause, no MySQL version comment, none of a short list of function names — or the reason it is refused. `view_query` goes the other way: from a stored `CREATE VIEW … AS <query>` statement it returns the query, what follows the first `AS` outside parentheses, strings and comments (used for SQLite, which keeps the whole statement). Pure functions, no I/O |
| `db::console` | The SQL console ([ADR 0015](docs/adr/0015-sql-console.md)). `Console` owns one connection detached from the session's pool and runs a script statement by statement over the simple/text protocol: impact guard, row cap, stop flag, tracking of the user's transaction and of MySQL autocommit, detection of a lost connection. It keeps the full rows of the last run for export. `Canceller` interrupts the console's statement from another pooled connection. `Console::read_only` runs one statement for a caller that must not be able to change anything (the AI's query tool, and "Preview rows" of the view form): `single_read`, then a `READ ONLY` transaction in which the server first prepares the statement and then runs it over the text protocol with a row cap, then `ROLLBACK` |
| `db::export` | Writes one stored result to a file as CSV, JSON or XLSX (`rust_xlsxwriter`). In JSON, columns that share a name get the keys `name`, `name_2`, `name_3`, … |
| `table_file` | Reads a file the user chose into rows of text for Smart Paste: delimited text (`csv`; UTF-8, UTF-16 by its byte-order mark, or an encoding the caller names through `encoding_rs`; the separator detected or given) or one sheet of a workbook (`calamine`: stored values, numbers with at most 15 significant digits, ISO dates). Accepts nine extensions, at most 64 MB, and returns at most the rows it is asked for together with the total |
| `ai_detect` | Locates `claude` / `codex` and reads their version and sign-in state. `locate`, `path_with` and `Provider::binary` are shared with `agent` |
| `agent` | The agent chat ([ADR 0016](docs/adr/0016-agent-chat-without-tools.md), [ADR 0017](docs/adr/0017-ai-database-tools.md)). Pure parts: the fixed instructions without tools (`SYSTEM_PROMPT`) and with them (`tools_prompt`), `validate_model`, `render_context` (schema text from catalogue metadata), `render_prompt` (instructions for Codex, context block, trimmed conversation), `arguments` (the fixed vector per provider, with or without the MCP server of the turn) and `StreamParser` (the CLIs' JSON lines to `Started` / `Delta` / `Message` events and an outcome; a Claude turn with tool calls is several messages joined into one answer). I/O: `models` (runs `codex debug models`), `chat` / `chat_with` (one CLI process per turn, in a process group of its own on Unix: prompt on stdin, events from stdout until the first verdict, stop flag, 10-minute timeout, the whole group killed on Stop or timeout). Given a `ToolSetup` (a session, a database, a schema, whether rows may be read, the bridge command), `chat_with` opens the turn's MCP endpoint before it starts the CLI, passes the tools' events (`ToolStarted`, `ToolFinished`, `Proposal`) to the caller between the CLI's lines, and drops the endpoint when the turn ends. Without one it holds no database session. It keeps no state between turns |
| `agent_tools` | The tools of one turn ([ADR 0017](docs/adr/0017-ai-database-tools.md)). `DbTools` implements `mcp::ToolHost` on an open `Session`, bound to one database and schema: `list_schemas` (engines with schemas), `list_tables`, `describe_table`, `run_select` (only when rows may be read; through `Console::read_only` on a console of its own, with a 30-second limit and cancellation when the turn's stop flag is set or the call is dropped) and `propose_sql` (validates and emits a `Proposal` event; runs nothing). `render_rows` is the text a query's rows are given to the model as. Every call emits a start and a finish event carrying exactly what the model was given |
| `mcp` | A Model Context Protocol server reduced to what a tool-calling client needs: JSON-RPC 2.0, one object per line, `initialize`, `ping`, `tools/list`, `tools/call`. `serve` answers one client over any reader and writer; `Endpoint` (Unix) is a socket in a private directory with a task accepting connections, removed on drop; `bridge` copies the process's stdin and stdout to such a socket. No dependency beyond tokio |
| `error` | `Error` serialised to the UI as `{ kind, message }` |

## Local data

| Data | Location | Notes |
|---|---|---|
| Profiles, UI settings, open tabs | `puricat.db` in the OS app-data directory for identifier `com.purivaro.puricat` (macOS: `$HOME/Library/Application Support/com.purivaro.puricat/`) | File mode 0600 on Unix. The identifier is a placeholder; changing it later orphans this data |
| Text of open query tabs | `puricat.db`, table `settings`, key `sql:<tab id>` | Written 600 ms after the last keystroke (a write still pending when the tab closes is dropped); written at once for a tab opened with SQL from the agent chat; set to an empty value when the tab closes |
| SQL history | `puricat.db`, table `query_history` | The script text of each run — of a query tab, or of a proposal of the AI that the user approved — with password literals masked, the connection id, database, status, a summary and the duration. The newest 1,000 rows over all connections are kept; a connection's rows are deleted with the connection. Clear text otherwise ([SECURITY.md](SECURITY.md)) |
| Query results | Backend memory, per query tab | The full rows of the tab's last run, replaced by the next run and dropped with the tab's console. Never written to disk except by an export |
| Exported files | Wherever the user saves them | Written by the backend; PuriCat keeps no record of them |
| Passwords | OS credential store | Never written to `puricat.db` |
| Backup settings and history | `puricat.db`, tables `backup_jobs` (one per database: folder, format, schedule, how many to keep) and `backup_runs` (every run: time, by hand or scheduled, outcome, tool, size, file, reason; the last 2,000) | Also read and written by the backup runner while the app may be open |
| Backup files | The folder the user chose | Mode 0600, not encrypted. PuriCat keeps no copy; retention deletes scheduled backups beyond the number to keep |
| The backup runner's lock and log | `backup-runner.lock`, `backup-runner.log` in the app-data directory | The lock keeps two runners from working at once; the log has one line per scheduled run |
| The LaunchAgent of scheduled backups | `~/Library/LaunchAgents/com.purivaro.puricat.backups.plist` | Exists only while some job has a schedule. Starts `puricat --run-backups --data-dir <app-data directory>` |
| Agent chat preferences | `puricat.db`, table `settings`, key `agent` | Provider, model per provider, the "Share context" switch, the access level of the database tools (`none`, `schema` or `data`; anything else is read as `none`) |
| Agent conversation | Web view memory (`stores/agent.ts`) | The turns, and with each sent message the exact context that went with it; with each answer its tool steps (what was asked, the exact text the model was given) and its proposals with their outcomes. Gone with "New chat" or when the app closes; never written to disk by PuriCat |
| The AI's undecided proposals | Backend memory (`AppState.proposals`), by id | Connection, database, SQL, provider, model, what the impact guard held back, and whether it is running. Removed when run, rejected or cleared with the conversation; lost when the app closes |
| AI activity log | `puricat.db`, table `agent_audit` | One row per row-reading query, refused or failed read, proposal, approval, rejection and outcome. SQL with password literals masked, clear text otherwise; no rows of data. The newest 5,000 rows are kept; not deleted with a connection ([SECURITY.md](SECURITY.md)) |
| The socket of a chat turn with tools | A directory `puricat-<16 hex digits>` (mode 0700) under the system temporary directory, holding `mcp.sock` | Created when the turn starts, removed when it ends |
| AI CLI scratch directory | `agent-scratch` in the app-data directory | The working directory of every chat turn. Created by the first turn; PuriCat writes nothing into it and tests assert that it stays empty |
| Theme hint | Web view `localStorage` key `puricat.theme` | Avoids a flash of the wrong theme before settings load |

## IPC surface

All commands are registered in `src-tauri/src/lib.rs` and implemented in `commands.rs`; the eight of the backups are in `backups.rs` and the three of the updater in `updates.rs`. Errors arrive as `{ kind, message }`.

| Command | Arguments | Returns |
|---|---|---|
| `list_connections` | — | Profiles, each with `hasPassword` |
| `save_connection` | `profile`, `password` (`keep` / `set` / `clear`) | Saved profile, `sessionClosed` |
| `duplicate_connection` | `id`, `name` | New profile (password copied inside the credential store) |
| `delete_connection` | `id` | — (closes the session, deletes the password, the connection's query history and its saved scripts) |
| `test_connection` | `profile`, `password` | `ServerInfo`; nothing is saved |
| `open_connection` | `id` | `ServerInfo`; session kept in `AppState` |
| `close_connection` | `id` | — |
| `list_databases` | `id` | Namespaces |
| `list_schemas` | `id`, `database` | Namespaces (PostgreSQL only) |
| `list_objects` | `id`, `database`, `schema?` | Tables, views, materialized views |
| `describe_table` | `id`, `table` | Columns, primary key and estimated row count of one table (used by the SQL editor's completion; the Empty and Drop forms of the table menu read the estimate) |
| `count_rows` | `id`, `table`, `filters`, `matchAny?`, `job` | `RowCount`: `count`, `elapsedMs`. `SELECT COUNT(*)` with the page's `WHERE` clause (the same conditions and the same `matchAny`), on a connection of its own; `cancel_job(job)` interrupts it and the call fails with `conflict` |
| `fetch_rows` | `id`, `table`, `page` (`offset`, `limit`, `sort?`, `filters?`: `column`, `op`, `value?`, `values?` — the list of `in` / `notIn`, the two ends of `between`; `matchAny?`: a row passes when any one condition holds, instead of all) | `RowPage`: columns (with `editable`), rows, truncation flags, primary key, estimated rows |
| `fetch_cell` | `id`, `table`, `key` (the complete primary key), `column` | `CellContent`: the cell's whole `value` as the page would render it (at most 1,000,000 characters, or 65,536 bytes in hex) and `cut` when even that was not all. Read-only; `conflict` when the row is gone |
| `plan_changes` | `id`, `table`, `changes` (`updates`, `inserts`, `deletes`) | The statements a save would run, in order: `kind`, `sql`, `params`, row label. Nothing is executed |
| `apply_changes` | `id`, `table`, `changes` | Counts of updated / inserted / deleted rows and elapsed time. One transaction; refused up front when the saved profile is read-only |
| `database_options` | `id` | `DatabaseOptions`, what the server offers for a new database. MySQL: `charsets` (`name`, `defaultCollation`, `description`), `collations` (`name`, `charset`), `defaultCharset`, `defaultCollation`. PostgreSQL: `owners`, `currentUser`, `templates`, `encodings`, `defaultEncoding`. The fields of the other engine are empty. Reads only; an error for a SQLite connection |

## Data flow: open a table

1. The user clicks a table in the explorer. `useWorkspace.openTable` adds or activates a tab and stores the tab list with `set_setting("workspace", ...)`.
2. The tab view, once visible and connected, calls `fetch_rows`; the page carries the column metadata, primary key and row estimate, so the structure view needs no second call. Hidden restored tabs do not query until shown.
3. `AppState::session(id)` returns the open `Session` (an error if the connection is not open).
4. `Session::fetch_rows` checks the page size (1–1000), reads table metadata from the catalogue with bound parameters, and resolves the order: the requested sort column must exist in the metadata, then primary-key columns are appended. The filter's conditions, if any, become a `WHERE` clause with their values as parameters (`db::filter`), joined with `AND` or, with `matchAny`, with `OR`; a condition the column cannot take, or a request over the limits, is refused here, before any SQL is sent.
5. The engine module builds one `SELECT` in which every column is rendered to text by the server, with identifiers quoted by `ident`, the filter's values bound first and `LIMIT`/`OFFSET` bound after them. It asks for `limit + 1` rows and one unit beyond each preview length.
6. `finish_page` trims to the limit, sets `hasMore`, cuts long cells on a character boundary, records them in `truncated`, and prefixes binary previews with `0x`.
7. The grid renders the page with row virtualization; a response superseded by a newer request is dropped.

## Data flow: save edits

1. Edits are staged in the tab view as a `Pending` value (`src/features/table/pending.ts`): cell edits keyed by row and column index, new rows, and rows marked for deletion, with a bounded undo history (the last 200 states). Typing, paste, clear, add row and delete only change `Pending`; nothing reaches the server. A cell set back to its original value is dropped from `Pending`.
2. Row indexes are stable because the page cannot change while edits are pending: paging, sorting, page size and refresh are locked, and a reload discards `Pending`.
3. On Save, `toChangeSet` translates `Pending` into a `ChangeSet`: each update and delete carries the row's complete primary key as loaded, each changed cell carries the original text and the new value, and each insert carries only the columns the user filled in (the rest take server defaults).
4. The tab decides whether the review step is required: a Production-labelled connection, any delete, or more touched rows than the connection's `bulkReviewRows` (default 10). The "Review" button always opens it. The review dialog calls `plan_changes` and shows each statement with its bound values (the first 60 in full, the rest counted). Small saves call `apply_changes` directly.
5. `apply_changes` refuses a profile saved as read-only, then `Session::apply_changes` reads the table metadata again and calls `write::plan` — the same function `plan_changes` uses — so the reviewed statements and the executed statements come from one code path. The plan is rebuilt at apply time from the same change set; it is not cached between the two calls.
6. `write::plan` validates the change set (non-empty, at most 10,000 row changes, known and editable columns, no column listed twice, complete non-NULL key in key order, updates and deletes refused on keyless tables) and emits statements in the order deletes, updates, inserts.
7. The engine module runs the statements in one transaction with values bound as text parameters. A driver error, or a statement that affects anything other than exactly one row, rolls the transaction back and returns a `database` or `conflict` error naming the row.
8. On success the tab reloads the page, which shows what the server stored and clears the staged edits. On failure the staged edits are kept and the message is shown.

The rules and their limits are in [SECURITY.md](SECURITY.md) and [DATABASE_COMPATIBILITY.md](DATABASE_COMPATIBILITY.md).

## Data flow: create a database

Decisions and limits: [ADR 0019](docs/adr/0019-schema-changes-through-forms.md). The rule is the one of a save — what is shown and what runs come from one function — applied to DDL, where nothing can be bound.

1. "New database…" in the explorer's menu of a connection (`Explorer.tsx`; shown only while the connection is open, and not for SQLite) puts that connection in the `ui` store (`newDatabaseOn`). `NewDatabaseDialog.tsx` mounts its form afresh for each opening.
2. The form calls `database_options`. `Session::database_options` reads the lists from the server with fixed queries on the pooled session — on PostgreSQL on the database the session was opened on (`home`). If the call fails the form says so and still works with the name alone.
3. The form holds only choices: the name and one value per list, where the first entry of a list means "leave it to the server" and is sent as no option at all. 120 ms after the last change it calls `plan_create_database` with them. `ddl::create_database` validates and returns the statement, or the reason it cannot be built; the form shows either. No SQL is built in the web view.
4. "Create database" calls `create_database` with the same choices. The command refuses a profile saved as read-only; `Session::create_database` builds the statement with the same function and hands it to the engine module's `execute_statement`: one `sqlx::raw_sql` statement on a pooled connection (MySQL), or on a pooled connection to `home` (PostgreSQL), outside any transaction.
5. On success the form shows a toast, expands the connection in the explorer, reloads its databases (`list_databases`) and closes. On failure it stays open with the server's message; the dialog cannot be dismissed while the statement is running.

Nothing is written to `query_history` or `agent_audit`.

## Data flow: edit or drop a database, flush

The same rule and the same record ([ADR 0019](docs/adr/0019-schema-changes-through-forms.md), section 7). One component, `DatabaseDialogs.tsx`, holds three forms and mounts the one named by `databaseTask` in the `ui` store afresh for each opening.

1. The explorer's menus (`Explorer.tsx`) set the task: "Edit database…" and "Drop database…" on a database (not for SQLite, and not where the listing marks the database as the server's own — which the MySQL listing does and the PostgreSQL listing does not), and the entries of "Flush" on a connected MySQL connection.
2. **Edit.** The form calls `database_details` and `database_options`, and fills its fields with the database as it is. From then on it builds a spec that holds only what differs; with nothing different there is no spec and no call. 120 ms after the last change it calls `plan_alter_database` and shows the statements, joined with `;` and a line break, or the builder's refusal. As in "New database", an answer is kept with the spec it belongs to, and "Save changes" works only while the statement on screen is the one for the choices on screen. Saving calls `alter_database` with the same spec.
3. **Drop.** The form calls `plan_drop_database` for the statement and `database_details` for the count; it works without the count. The button is enabled while the text typed equals the name. Dropping calls `drop_database` with the name and the typed text; the command compares them itself.
4. **Flush.** The form calls `plan_flush`, shows the statement under a sentence about it, and "Run" calls `flush_server`.
5. In the backend, a drop or a rename first gives the database up: `AppState::release_consoles` removes the consoles of query tabs opened on it (a running statement is interrupted; the tab's next run opens a new console), and on PostgreSQL `PgSession::release` closes the session's pool for it. The statements then run through `execute_statement` on a pooled connection — on PostgreSQL to the database the session was opened on, the alter statements as one simple query.
6. After a drop or a rename the form calls `databaseGone` in the `workspace` store (the database's table tabs close; its query tabs keep their text and get the new name, or `null`, the connection's default database), `forgetDatabase` in the `connections` store (the schemas, objects and expanded nodes loaded under the old name) and reloads the database list. A change that is not a rename reloads nothing.

"Open SQL file…" is not a form: the menu item calls `pick_sql_file` and hands the returned text to `openSql`, which opens a query tab seeded with it, as a saved script is opened. Nothing of all this is written to `query_history` or `agent_audit`.

## Data flow: the table menu

The same rule again ([ADR 0019](docs/adr/0019-schema-changes-through-forms.md), section 8). One component, `src/features/schema/TableDialogs.tsx`, holds the definition view and two forms (rename; empty and drop share one) and mounts the one named by `tableTask` in the `ui` store afresh for each opening. The pieces these dialogs share with `DatabaseDialogs.tsx` — the header with the connection, the statement box, the notices, the failure line, the footer — are in `src/features/schema/parts.tsx`; they were moved there from `DatabaseDialogs.tsx` without a change of behaviour.

1. The explorer's menu of a table, a view or a materialized view (`Explorer.tsx`) sets the task: its kind (`definition`, `rename`, `empty`, `drop`), the connection, the `TableRef` and the object's kind. "Rename…" is left out for a SQLite view, "Empty table…" for anything but a table.
2. **Definition.** The view calls `table_definition` and shows the text with the note for its `source`. "Copy" writes the text to the clipboard; "Open in query tab" hands it to `openSql` with the table's database, as a SQL file is opened. Nothing runs.
3. **Rename.** The field starts with the current name. While the trimmed text is empty or the same there is no change and no call; otherwise, 120 ms after the last keystroke, the form calls `plan_table_change` and shows the statement or the builder's refusal. As in the database forms, an answer is kept with the change it belongs to, and "Rename" works only while the statement on screen is the one for the name on screen. It calls `apply_table_change` with `typed` `null`.
4. **Empty, Drop.** The form calls `plan_table_change` once and, for a table, `describe_table` for the row estimate; it works without the estimate. The button is enabled while the text typed equals the table's name. It calls `apply_table_change` with the change and the typed text; the command compares them itself.
5. In the backend `apply_table_change` refuses a profile saved as read-only, checks `typed` for anything but a rename, and calls `Session::table_change`: the builder again, then one `sqlx::raw_sql` statement — on a pooled connection (MySQL), on a pooled connection to the table's database (PostgreSQL, `execute_on`), or on the writable handle (SQLite).
6. Afterwards the form tells the `workspace` store: `tableGone` after a rename or a drop (the table's tab closes), `reloadTable` after an empty (a counter per tab id in `reloads`, which the table tab's page and count effects depend on, so an open tab reads its rows again). After a rename or a drop it also reloads the explorer's object list for that database and schema (`loadObjects`). All three forms are held back while `dirty` has the table's tab id.

Nothing is written to `query_history` or `agent_audit`.

## Data flow: the view form

The same rule for the words of the statement, and another one for the query ([ADR 0019](docs/adr/0019-schema-changes-through-forms.md), section 9). One component, `src/features/schema/ViewDialog.tsx`, serves "New view…" and "Edit view…" and mounts its form afresh for the task in `viewTask` of the `ui` store; it uses the shared pieces of `parts.tsx`.

1. The explorer (`Explorer.tsx`) sets the task. `new`, with the connection, the database and the schema or `null`: from the menu of a database where the engine has no schemas (MySQL, SQLite), of a PostgreSQL schema — both only where the listing does not mark the row as the server's own — and of a "Views" group. `edit`, with the connection and the `TableRef`: from the menu of an object of kind `view`.
2. An edit first calls `view_select` and waits for the answer; a failure is shown in place of the editor. The name field is disabled.
3. The editor is the app's SQL editor: the form imports `src/features/sql/monaco` — the lazy chunk a query tab loads — and calls its `createEditor` with the engine's grammar, the query as its text, and a schema source for the suggestions (table names from what the `connections` store has loaded for the connection, columns through `describe_table` in the view's database and schema). ⌘↵ in the editor previews. The dialog ignores a click outside it, and Escape while the focus is in the editor, so that neither throws a query away.
4. With a name and a query the form builds a `ViewSpec` and, 200 ms after the last change, calls `plan_view`. `ddl::view_statements` returns the statements, or the reason there are none; the form shows either, each statement ended with `;`. As in the other forms an answer is kept with the spec it belongs to, and the button works only while the statement on screen is the one for the name and the query on screen.
5. "Preview rows" calls `preview_view_select` with the database and the query as it is in the editor. `Session::preview_select` checks the text with `ddl::view_query`, opens a reader (`open_reader`: a console on that database; on SQLite a handle that cannot write), runs `Console::read_only` for at most 100 rows and looks every 150 ms whether 15 seconds have passed, in which case it cancels the statement on the server. The form shows the rows in a small table with their number and the time, or the error; when the editor's text no longer is the text that was tried, both are dimmed and the form says that the query changed.
6. "Create view" / "Save view" calls `save_view` with the same spec. The command refuses a profile saved as read-only; `Session::save_view` builds the statements again and runs them — see `db::ddl` for where. On MySQL and PostgreSQL it runs through `Session::execute_one`, which sends one statement over the protocol that takes one statement only (a prepared statement; the extended protocol), so the server too refuses a text that holds a second one; on SQLite the drop and the create run in one transaction, and the query holds no semicolon.
7. Afterwards the form opens the "Views" group of the database or schema in the `connections` store, reloads its object list (`loadObjects`) and, after an edit, calls `reloadTable` in the `workspace` store so that an open tab of the view reads again. On failure it stays open with the server's message; it cannot be dismissed while the statement runs.

Nothing is written to `query_history` or `agent_audit`. As a query tab does, the form attaches its editor object to its `<form>` element as `__editor`, in every build, for the end-to-end test.

## Data flow: users and privileges

The rule of the schema forms, with a password in the statements ([ADR 0023](docs/adr/0023-users-from-templates.md)). One component, `src/features/schema/UsersDialog.tsx`, holds the list, the pane of one account and three forms; its pure helpers are in `users.ts` (the account written as `user@host`, the search, which accounts the forms leave alone, the spec sent for the form's choices, the password generator, the grouping of the statements). It uses the header and the notices of `parts.tsx`.

1. "Users and privileges…" in the explorer's menu of a connection (`Explorer.tsx`; while it is connected, and not for SQLite) puts the connection in `usersOf` of the `ui` store. The dialog mounts its content afresh for each opening and calls `list_accounts`.
2. **The list and the pane.** The search box filters the list in the web view, by a part of the name or the host, whatever the case. Selecting an account calls `account_details`; the pane shows MySQL's grants as the server printed them, one statement per line with `;`, or PostgreSQL's attributes, memberships and table of databases. "Change password…" and "Drop user…" are disabled, with the reason as their tooltip, for a read-only connection and for the accounts marked `you`, `system` or `superuser`.
3. **New user.** The form lists the databases with `list_databases`, leaving out those the listing marks as the server's own (MySQL's four; PostgreSQL's listing marks none). From the template, the name, the host (MySQL: `%`, `localhost` or one typed), the database and the password it builds a `UserSpec` — the host only on MySQL, a database only for the first two templates, the password as typed — and, 150 ms after the last change, calls `plan_user` with it and the state of "show". The statements come back grouped: those on the server, then "Inside database …" for PostgreSQL's. As in the other forms an answer is kept with the spec and the "show" state it belongs to, and "Create user" works only while the statements on screen are the ones for the choices on screen, a password has been typed and the connection is not read-only. "Generate" (`generatePassword`: 24 letters and digits from `crypto.getRandomValues`, bytes that would favour some characters thrown away) fills the field and turns "show" on. On MySQL the form adds a sentence when the database name had `_` or `%` escaped; on PostgreSQL two sentences on `ALTER DEFAULT PRIVILEGES` (naming the connection's own role) and `PUBLIC`.
4. "Create user" calls `create_user` with the same spec. The command refuses a profile saved as read-only; `Session::create_user` builds the statements again — on MySQL for the mode read on the connection it then runs them on — and runs them, undoing the creation when a later step fails (see `db::users`).
5. **Change password, drop.** The password form calls `plan_password` 150 ms after each change, with an empty password too (the statement then shows the mask), and "Change password" calls `change_password`. The drop form calls `plan_drop_user` once; its button is enabled while the text typed equals `accountLabel` (`user@host` on MySQL) and the connection is not read-only, and "Drop user" calls `drop_user` with the typed text, which the command compares itself.
6. Afterwards: a creation reloads the list, selects the new account and shows the password, in view, with "Copy" and the note that PuriCat does not keep it; a password change shows the new password the same way; a drop reloads the list and clears the selection. On failure the form stays open with the server's message, scrubbed of the password. While a statement runs the dialog cannot be dismissed. While a form or the password screen is open, a click outside the dialog is ignored, and Escape in a form returns to the list instead of closing the dialog, and what the form held is gone then; the screen that shows a new password ignores Escape and a click outside, and stays until "Done".

Nothing is written to `query_history` or `agent_audit`, and nothing of the dialog is persisted: the list, the details, the forms and the password are component state, gone when the dialog closes.

## Data flow: Smart Paste

1. "Smart Paste…" is shown on an editable table tab and is disabled while the tab has unsaved edits. The dialog reads the system clipboard through the clipboard plugin and parses it with the same TSV parser as direct paste. It also calls `unique_keys`. "Open a file…" replaces the clipboard as the source: `pick_table_file` shows the Open dialog and `read_table_file` returns the file's rows as text (`table_file`); from there the steps below are the same. A file with more than 10,000 data rows is not offered for mapping.
2. Set-up happens in the web view (`src/features/table/smartPaste.ts`, pure functions): header-row detection (the first row is a header when at least half of its non-empty cells name table columns, case-insensitively, and there is a second row), automatic mapping (by header name, otherwise by position; a table column receives at most one pasted column), the mode, the key (only keys whose columns are all mapped are offered; UPDATE and UPSERT always use one, the first usable unless the user picked another) and the columns to update. `buildRequest` drops the header row, unmapped columns and completely empty rows, and types empty cells: NULL for a key column and for every non-text column (also a NOT NULL one), an empty string for a text column; the literal text `NULL` becomes NULL only when the option is on.
3. Preview calls `analyze_paste`. `Session::prepare_paste` reads the table metadata and unique keys and builds a `smart::Draft`, which refuses a set-up that cannot work (unknown or doubly mapped columns, a key that is not a unique key of the table or is not fully mapped, a key column in the update list, a non-writable column that is not part of the key) and finds missing keys, malformed key values (a key value for an integer column must be a whole number; other key columns get the value pre-checks) and exact-text duplicates without a query. Such rows are never sent to the database.
4. For the remaining rows `Draft::lookups` produces one parameterised `SELECT` per 40 pasted rows. Each returns, for every existing row matched by the chunk, one boolean flag per pasted row followed by the key and update columns rendered as text. The session runs them; `Draft::matched` records the hits and remembers each matched existing row by its key as the database rendered it, so a second pasted row reaching the same existing row — in the same lookup or another — makes both duplicates. Because the comparison happens in the database, its own type and collation rules decide which rows are the same.
5. `Draft::finish` classifies every pasted row (insert, update with the changed columns, unchanged, unmatched, missing key, duplicate, exists, invalid), applies the pre-checks to the values that would be written, and builds a `ChangeSet` and a fingerprint of every row's status and changed columns. The preview shows the counts and the first 200 rows; nothing has been written. The UI ties the preview to the exact request, so any change to the set-up makes it stale and disables Run.
6. Run calls `apply_paste` with `expected` set to the preview's fingerprint. The command refuses a read-only profile, registers a cancel flag under the job id in `AppState.jobs`, and `Session::apply_paste` runs `prepare_paste` again. Unless the fresh analysis produces the same fingerprint it returns a `conflict` error and nothing runs; equal counts are not enough. Rows with a problem are not in the change set; they make the run refuse, unless the request carries `skipProblems` (the preview's "Leave these rows out" checkbox), in which case the statements for the other rows run.
7. Otherwise the change set goes through `write::plan_keyed` — the planner behind `write::plan`, addressing rows by the chosen key as the database rendered it instead of the primary key. UPDATEs carry the optimistic check on the values seen by this fresh analysis.
8. The engine module executes the statements in one transaction, each required to affect exactly one row. Before every statement it calls back into the command, which reports progress over the channel every 20 statements and reads the cancel flag; `cancel_job` sets that flag. A cancel, a driver error or a wrong row count rolls everything back. The lookups of step 6 run on pooled connections before this transaction starts, not inside it. While the run is in flight the dialog cannot be dismissed (Esc, outside click and the close button are blocked); "Stop and roll back" is the way out.
9. On success the dialog closes and the tab reloads the page. On failure the message is shown and a new preview is required.

## Data flow: run a script in a query tab

Decisions and limits: [ADR 0015](docs/adr/0015-sql-console.md).

1. "New query" (explorer context menu on a connection or a database, the command palette, ⌘T) calls `useWorkspace.openSql`, which adds a tab of kind `sql` with an id `sql:<uuid>`, the connection id, a database (or none, for the connection's default) and a title "Query n". The tab view (`src/features/sql/SqlTab.tsx`) and Monaco are separate chunks that load now; the saved text of the tab is read from the settings store. A tab opened from the agent chat ("Open in query tab") starts instead with the SQL it was opened with, and runs nothing. A tab can be a saved script: ⌘S (or the Save button) asks for a name once and stores the text with `create_script`; the tab then carries the script's id (`scriptId`, kept with the workspace) and its name as the title, and ⌘S writes the text back with `update_script`. The tab compares its text with the stored text (`get_script` when it opens) and reports a difference to the workspace (`edited`), which shows a dot on the tab and asks before closing it (Save, Don't save, Cancel). "Saved scripts" in the tab lists the connection's scripts (`ScriptsMenu.tsx`): opening one brings its tab to the front, fills the tab in front when that is blank, or opens a new tab; renaming and deleting are done there, and the open tabs follow (`renameScript`, `unbindScript`).
2. ⌘↵ or Run takes the selection, or the whole text when nothing is selected, and calls `analyze_sql`. ⇧⌘↵ ("Run the statement at the cursor", in the menu beside Run) takes one statement instead: the whole text goes to `analyze_sql`, `statements.ts` converts the answer's byte offsets to the editor's UTF-16 offsets and picks the statement the cursor belongs to — from its first word to the end of the line it ends on; on a later line, the next one — and that statement's text is what runs. The same answer, asked again 200 ms after each change, draws the mark in the editor's margin beside that statement when the script has more than one. `script::split` scans the text with the engine's lexical rules and returns the statements with their kind and danger reason. If any statement has a danger reason — or, on a Production-labelled connection, is not a `read` — the tab lists those statements and waits for the user's confirmation.
3. `run_sql` receives the text, the tab id, the tab's database and the options: `maxRows` from the tab's "Rows per result" selector and `changeLimit` from the connection's `bulkReviewRows`. The command finds the tab's console in `AppState.consoles` or opens one: `Session::open_console` acquires a connection from the session's pool (so strict mode and the read-only statement have run on it), issues `USE` for the chosen database on MySQL or takes the pool of the tab's database on PostgreSQL, detaches the connection from the pool, and notes the server's connection id or backend pid for cancelling.
4. `Console::run` splits the script again and runs the statements in order. For each one it decides: *guarded* (a `dml` statement while no transaction of the user's is open and, on MySQL, autocommit is on) and *cancel at the cap* (a `read`, and not inside a user's transaction on PostgreSQL).
5. A guarded statement is wrapped in `START TRANSACTION` / `BEGIN` … `COMMIT`. The statement goes out with `sqlx::raw_sql(...).fetch_many`; rows arrive as text and are decoded per engine (binary as `0x…`, MySQL `BIT` as a number). Rows beyond `maxRows` are not kept; at that point a cancellable statement is interrupted through the `Canceller`, any other is read to its end.
6. After the statement: an error, a stop request or — for a guarded statement — more affected rows than `changeLimit` turns the `COMMIT` into a `ROLLBACK`, and the statement is reported as `error`, `cancelled` or `blocked`. A `blocked` statement sets `resume` to the text from that statement to the end of the script. Any status other than `ok` ends the run; the statements not reached are counted in `skipped`.
7. The console then updates what it knows about the session. After a successful statement: `transaction_effect` for a transaction-control statement, and an implicit commit after MySQL DDL, except `CREATE` / `DROP TEMPORARY …`, which do not commit (recognised by `TEMPORARY` being the statement's second word). After any `other` statement on MySQL the remembered `@@autocommit` is forgotten and asked again when next needed. A successful `read` that returned no rows is described to get its column names. Each result set is stored in full in the console and returned as a preview with cells cut to 1,000 characters.
8. The command records the run in `query_history` (text masked by `script::redact`) and, if the connection was lost, removes the console so the next run opens a new one.
9. The tab shows one result tab per result set in the shared grid (read-only, not sortable) and a Messages list. `inTransaction` sets the tab's dirty flag, which drives the same guards as staged edits. For a `blocked` statement, "Run it without the limit" calls `run_sql` with `resume` and no `changeLimit`.
10. Stop calls `cancel_sql`: the stop flag is set and the `Canceller` sends `KILL QUERY` or `pg_cancel_backend` on a pooled connection; if the command fails, the tab shows the error. Export, which is disabled while a run is in flight, asks the Save dialog for a path and calls `export_result`, which writes the stored result with `db::export`. Closing the tab calls `close_console`, clears the saved text and drops a save that was still pending.

## Data flow: one agent chat turn

Decisions and limits: [ADR 0016](docs/adr/0016-agent-chat-without-tools.md) and [AI_INTEGRATION.md](AI_INTEGRATION.md). This is the turn with the database tools off, which is the default: the model gets no tools and no database access, and the flow only moves text. What a turn with tools adds is the next section.

1. The AI panel (`components/layout/AiPanel.tsx`) calls `detect_ai_clis` when it appears and loads the chat preferences from setting `agent`. It shows the chat (`features/agent/AgentChat.tsx`) for the selected provider only when that CLI is installed and not known to be signed out. The model selector calls `agent_models`.
2. The chat derives its scope from the tab in front: the connection, database and schema of a table tab, or the connection and database of a query tab together with that tab's id. With no table or query tab, a closed connection or no database there is no scope.
3. Send (Enter or the button) calls `useAgent.send`. The store appends the user's turn and marks a turn as starting, so a second Enter cannot start another; Stop or "New chat" at this point gives the claim up and nothing is sent. If "Share context" is on and there is a scope, it calls `agent_context` with the scope and, for a query tab, the editor's current text — read through `sqlEditors`, a map from tab id to a getter that every mounted query tab registers.
4. `agent_context` takes the open `Session`, reads `server_info`, `list_objects`, and `describe_table` for the first 40 objects one after another, and returns `agent::render_context(...)`: names and types only. The store records that text on the user's turn; it is what "Context sent" shows. If the call fails, the message is sent without context.
5. The store appends an empty assistant turn and calls `agent_send` with a new job id and the request: the provider, the model chosen for that provider (or none), the context text, the transcript — every earlier turn except answers that ended in an error — and `tools`, which is `null` when the access level is "Off" or the question was asked without a table or query tab in front.
6. The command registers a cancel flag under the job id in `AppState.jobs` and calls `agent::chat`, which locates the binary (`ai_detect::locate`), validates the model name, builds the prompt (`render_prompt`: for Codex the fixed instructions, then the context block, then the most recent turns up to 60,000 characters) and creates the scratch directory if it does not exist.
7. The CLI is spawned with the fixed vector from `arguments(...)`, the scratch directory as its working directory, all three standard streams piped and, on Unix, a process group of its own. Two tasks run beside the turn: one writes the prompt to stdin and closes it, one keeps the tail of stderr. The turn itself reads stdout line by line, each line going through `StreamParser::line`; before every read, and at least every 150 ms, it looks at the stop flag and at the 10-minute deadline.
8. The parser's events go over the channel as they come: `started` (with the model the CLI names), `delta` (text to append) and `message` (the whole answer so far, replacing what was streamed). The store patches the assistant turn, and the chat renders its text through `parseMarkdown` into React elements on every change.
9. The turn ends in one of four ways. With the parser's verdict, as soon as a line carries one: success returns the complete answer, failure returns the CLI's own message. With the CLI closing its output without a verdict: exit status 0 with some text is a success, anything else fails with the last line of stderr. In both cases the CLI gets 5 seconds to exit by itself before it is killed. On Stop: `cancel_job` sets the flag, the reader sees it, the CLI's process group is killed and the command returns a `conflict` error "Stopped". On timeout: the same kill, and the error names the limit. The command then removes the job's flag.
10. The store marks the assistant turn `done`, `stopped` (keeping the text that had arrived) or `error` (keeping the message). "Try again" drops that turn and repeats steps 5–10 with the context recorded in step 4.
11. "Open in query tab" on a SQL block calls `useWorkspace.openSql(connectionId, database, text)` with the scope recorded on the question. The store keeps the text as the new tab's seed and saves it under the tab's settings key; the tab view starts its editor with it. Nothing is sent to the database. Running it is the flow of the previous section, with its confirmation, impact guard and row cap.

## Data flow: an agent turn with database tools, and an approved proposal

Decisions and limits: [ADR 0017](docs/adr/0017-ai-database-tools.md) and [AI_INTEGRATION.md](AI_INTEGRATION.md), "Database tools". The steps of the previous section still happen; these are the differences.

1. The access button (`AccessButton` in `AgentChat.tsx`) sets the level in the `agent` store — `none`, `schema` or `data` — which is saved in setting `agent`. When a turn starts, `toolScope` turns the level and the target recorded on the question into the request's `tools`: the connection id, database and schema of that tab, and `readRows` for the level `data`.
2. `agent_send` takes the open `Session` of that connection (an error if it is not open) and builds a `ToolSetup` whose bridge command is the path of the running executable followed by `--mcp-bridge`.
3. `agent::chat_with` starts the tools before the CLI (`ToolRun::start`): it creates a channel for tool events and a stop flag, wraps the session in `agent_tools::DbTools`, and opens an `mcp::Endpoint` — a directory with mode 0700 under the temporary directory, a Unix socket in it, a task that accepts connections. The socket's path is appended to the bridge command.
4. `arguments(...)` builds the vector with that command: for Claude Code `--mcp-config` with the one server, `--strict-mcp-config`, `--allowedTools mcp__puricat`, `--setting-sources ""` and the instructions of `tools_prompt` as `--system-prompt`; for Codex two `-c mcp_servers.puricat.…` overrides, with `tools_prompt` leading the prompt on stdin.
5. The CLI starts its MCP server: PuriCat's executable with `--mcp-bridge <socket>`. That process's `main` sees the argument first, calls `mcp::bridge` and never initialises the app; it copies its stdin to the socket and the socket to its stdout until either side closes.
6. `mcp::serve` answers the CLI on that connection: `initialize`, `tools/list` (what `DbTools::tools` offers for this engine and level) and each `tools/call`, which goes to `DbTools::call`.
7. `DbTools::call` emits `ToolStarted`, runs the tool and emits `ToolFinished` with exactly the text it returns. The catalogue tools call `Session::list_schemas`, `list_objects`, `describe_table` and `unique_keys` on the pooled session. `run_select` checks the text with `script::single_read`, opens a console of its own on the database (`Session::open_console`) and calls `Console::read_only`; a loop beside the query looks at the turn's stop flag and at a 30-second limit every 150 ms and cancels the query through the console's `Canceller`. `propose_sql` splits and classifies the text and emits a `Proposal` event with a new id; it sends nothing to the database.
8. In `chat_with` the reader takes whichever comes first, a line from the CLI or a tool event, preferring a line that is already there, and passes both to the command's callback. `agent_send` forwards every event over the channel, and on the way: remembers the model the CLI named; stores each `Proposal` in `AppState.proposals` with the connection, database, provider and model; and notes each finished `run_select` (`read` or `read_failed`) and each proposal (`proposed`) for the activity log.
9. The store patches the assistant turn: a `toolStarted` event adds a step at the current length of the answer's text, `toolFinished` completes it, `proposal` adds a pending proposal. `AnswerBody` renders the text with the steps (`ToolSteps`) and proposal cards (`ProposalCard`) at those positions.
10. When the turn ends, `chat_with` sets the tools' stop flag, hands over the events still in the channel and drops the endpoint: the socket's directory is removed and its connections end. `agent_send` then writes the noted entries to `agent_audit` (`Store::add_audit`, SQL through `script::redact`). The store marks steps that never got an answer as failed.
11. The next question resends the conversation through `transcript(...)`, which adds under each answer one line naming the tools that were called and one line per proposal with what became of it.

An approved proposal:

1. "Review and run…" on a card opens the review dialog (in `AgentActivity.tsx`), built from the proposal held in the web view and the connection's profile. "Approve and run" calls `useAgent.decide(id, "approve")`, which calls `agent_proposal_run` with the id and `liftLimit: false`. No SQL crosses IPC.
2. The command finds the proposal in `AppState.proposals`, refuses one that is running, and marks it running. `run_proposal` reads the connection's profile, refuses a read-only one, logs `approved`, and calls `run_on_console` — the function behind `run_sql` — with the stored SQL, the console name `proposal:<id>`, the proposal's database, `maxRows` 200 and `changeLimit` set to the profile's `bulkReviewRows`.
3. `Console::run` executes the script as for a query tab (steps 4–7 of "run a script in a query tab"), including the impact guard and the history entry. The command then removes the console, which rolls back a transaction the script left open, and logs `executed`, `blocked` or `failed` with a summary.
4. If a statement was blocked, the proposal stays in `AppState.proposals` with `resume` — that statement and the rest of the script — and the card offers "Run without the limit…". Confirming it calls `agent_proposal_run` with `liftLimit: true`, which runs `resume` with no `changeLimit`; the store puts the new outcome after the statements that had already run. If the run ended any other way the proposal is removed; if it could not start, it is kept and the card shows the error.
5. "Reject", "Don't run it" and "New chat" call `agent_proposal_reject`, which removes the proposal and logs `rejected`. Stop on a running proposal calls `cancel_sql` with `proposal:<id>`.
6. The history icon in the AI panel opens `ActivityLog.tsx`, which calls `agent_audit` with a limit of 500; "Clear log" calls `clear_agent_audit`.

## Data flow: a backup

Design: [ADR 0021](docs/adr/0021-backups-with-dump-tools.md).

1. "Back up…" in a database's menu sets `ui.backupOf`; `BackupDialog.tsx` calls `backup_plan`, which asks the open session for the server's version, probes the dump tools on the computer and chooses one.
2. "Choose…" calls `pick_backup_folder` (the backend shows the dialog). "Back up now" calls `run_backup`: the settings are saved as the database's job, the password is read from the credential store, and `backup_schedule::perform` runs.
3. `backup::run` starts the tool with its fixed vector, writes its output (gzipped if asked) to `.<name>.partial`, reports the size as it grows, checks the closing line or has `pg_restore` list the archive, and renames the file. `perform` writes the run into `backup_runs` whatever happened.
4. "Save schedule" calls `save_backup_job`, which stores the job and brings the LaunchAgent in line with all jobs (`launchd::sync`: write the property list, `launchctl bootout`, `launchctl bootstrap`; or remove it).
5. At a scheduled time launchd starts `puricat --run-backups --data-dir <dir>`. `main.rs` sees the first argument and calls `backups::run_backups` instead of starting the app: lock, open the store, `backup_schedule::run_due` with passwords from the Keychain, one log line per run, a notification for a failure.
6. `run_due` runs each job whose scheduled time has passed since its last scheduled run and since it was saved; after a backup that was kept it deletes the job's scheduled backups beyond the number to keep.

## Data flow: an update

Design: [ADR 0020](docs/adr/0020-in-app-updates.md).

1. Once the settings are loaded, `App.tsx` calls the `updates` store's `check(true)` if `autoUpdate` is on. The version in the status bar, the palette's "Check for updates…" and the application menu's "Check for Updates…" (a menu event, `menu:check-updates`) call `check()`, which also opens `UpdateDialog.tsx`.
2. `check_update` builds the plugin's updater (in a debug build only with the address in `PURICAT_UPDATE_ENDPOINT`), asks the manifest, and stores the `Update` it found in `AppState.update`. The web view gets the version, the date and the notes.
3. A version that was found replaces the version number in the status bar. Nothing else happens until the user chooses "Download and install".
4. `install_update` takes the stored `Update`, refuses unless the process runs from an app bundle, and calls the plugin's `download_and_install`: the package is downloaded into memory (progress goes to the web view every 256 KB), its signature and signed version are verified, and the bundle on disk is replaced, with the old one moved aside until the new one is in place.
5. The dialog then offers "Restart now" (`restart_app`). With tabs that hold staged edits, an open transaction or an unsaved script it says how many first.

## Sessions and pools

| Engine | Pooling |
|---|---|
| MySQL | One pool per connection, max 4 connections |
| PostgreSQL | One pool per database, created on first use, max 3 connections each (a PostgreSQL connection is bound to one database) |

Both: idle timeout 600 s; acquire timeout equals the profile's connect timeout; a direct probe connection is made before the pool so the user sees the driver's real error; the read-only statement runs on every new pooled connection.

Query tabs do not use these pools for their statements. Each tab that has run something holds one connection of its own, acquired through the pool (so the same set-up has run on it) and then detached, which frees the pool slot; six open consoles next to a working session are covered by a live test. There is no limit on the number of consoles other than the server's connection limit. The pool is still used to send a Stop or a row-cap interrupt. The AI's query tool and an approved proposal use the same kind of connection: one per `run_select` call, one per run of a proposal, each closed when the call or the run is over. The "New database" form is the exception in the other direction: its one statement runs on a pooled connection, not on a console. So do the statements of the database menu (alter, drop, flush). The view form uses both kinds: its save runs on a pooled connection on PostgreSQL and on the writable handle on SQLite, but on MySQL on a connection taken out of the pool and closed afterwards, because it issues `USE` first and the chosen database must not stay behind on a pooled connection; and each "Preview rows" opens a console of its own, as one `run_select` call of the AI does, and drops it when the rows are back. A drop or a rename is also the one place where connections are closed on purpose while the session stays open: the PostgreSQL pool for that database (`PgSession::release`; a later use opens it again) and the consoles of query tabs on it (`AppState::release_consoles`). The users dialog, on MySQL, creates a user and changes a password on a connection taken out of the pool and closed afterwards, because the literal that holds the password is written for the `sql_mode` read on that very connection; its reads, a drop, and everything it does on PostgreSQL go through the pools — on PostgreSQL the role and its `CONNECT` through the pool of `home`, the grants inside a database through that database's pool.

Session settings: every MySQL connection adds `STRICT_ALL_TABLES` to its session `sql_mode` and otherwise keeps the server's defaults (the driver's own defaults of forcing the time zone to UTC and enabling `PIPES_AS_CONCAT` are turned off). PostgreSQL connections run with `TimeZone=UTC`, which the driver sends at start-up and PuriCat does not yet override (see [DATABASE_COMPATIBILITY.md](DATABASE_COMPATIBILITY.md)). Sessions live in `AppState` keyed by connection id; consoles live there keyed by tab id. Pooled sessions have no reconnect logic yet, and browse, catalogue and lookup queries cannot be cancelled (Phase 2b). What can be stopped: a Smart Paste run, between statements, and the statement a query tab is running, on the server. A query tab whose connection was lost opens a new one on its next run.

## Frontend state

| Store (`src/stores`) | Holds | Persisted |
|---|---|---|
| `connections` | Profiles, session state per connection, lazily loaded explorer levels, expanded nodes; `forgetDatabase` drops what was loaded under a database that was dropped or renamed | Profiles only, in the backend store |
| `workspace` | Tabs (welcome, table, query) and the active tab; `dirty` (table tabs with unsaved edits, query tabs with an open transaction) and `closing` (a dirty tab waiting for the user's confirmation). `hasUnsavedInDatabase` answers for the tabs of one database, and `databaseGone` (the pure `databaseGoneIn`) closes the table tabs of a dropped or renamed database and moves its query tabs. For the table menu: `tableGone` closes the tab of a renamed or dropped table, and `reloadTable` raises that tab's counter in `reloads`, which makes an open tab read an emptied table again; the view form calls `reloadTable` after an edit. Beside the store, two module-level maps: the text a query tab was opened with (`sqlSeed`, until the tab closes) and a getter for each mounted query tab's editor text (`sqlEditors`, read for the agent's context) | Tabs and active tab only, in setting `workspace` |
| `settings` | Theme, language, panel visibility and widths, and whether to look for an update at start-up (`autoUpdate`) | Setting `ui` |
| `updates` | What the last update check found, the state of the dialog, the download's progress and the last failure | No |
| `ui` | Dialog and palette open state; the connection the "New database" form was opened on (`newDatabaseOn`); the edit, drop or flush a menu asked for (`databaseTask`); the definition, rename, empty or drop the menu of a table or a view asked for (`tableTask`); the view to make or to edit (`viewTask`); the connection whose users and privileges are open (`usersOf`) | No |
| `agent` | Chat preferences (provider, model per provider, "Share context", the access level of the database tools); the conversation's turns, each user turn with the context sent and the tab scope it was asked about, each assistant turn with its tool steps and its proposals (state and outcome); the job id of the running turn | Preferences only, in setting `agent` |

The Smart Paste dialog keeps its own state (pasted block, mapping, preview) and is created afresh on every opening. So is the "New database" form (the name, the choices, the server's lists and the statement the backend returned), and so are the forms of the database menu and of the table menu, the view form with its query and its previewed rows, and the users dialog with its list, its forms and the password of an account being made or changed. Table data, the whole values fetched for shortened cells (they amend the loaded page, which is what makes such a cell editable), the sort, the filter's conditions and staged edits (`Pending` plus its undo history) are local component state in the tab view and are never persisted (a restored tab opens unfiltered); the tab reports only a dirty flag to the `workspace` store. That flag drives the unsaved dot on the tab, the confirmation before closing a dirty tab, bulk closes that keep dirty tabs open, and the refusal to disconnect, delete or re-save a connection that has dirty tabs. A query tab sets the same flag while the last run reported an open transaction, so all of these apply to it too (the dialog then offers "Roll back and close"). The query tab's results, the chosen row cap and the editor height are local component state and are not persisted; its text is (see "Local data"). `src/lib/types.ts` mirrors the serde types in `crates/core` by hand.
